# 测试标准

> 任何 Agent 或开发者读完后，都能明确知道：测什么、测到什么程度、按什么顺序、怎么写。

---

## 一、核心原则

### 1. 测试的目标是信任，不是覆盖率

测试的目的是：**当代码出问题 时，能在上线前发现**。

不是：
- 追求 100% 覆盖率
- 为了覆盖率写无意义的测试
- 用测试数量评价团队

### 2. 故障导向：按故障影响决定测试优先级

| 故障影响 | 示例 | 测试优先级 |
|---------|------|----------|
| 用户数据丢失 | 数据库写入错误、文件删除 | P0 |
| 安全漏洞 | 未授权访问、权限绕过 | P0 |
| 金钱损失 | 计费逻辑错误、支付流程 | P0 |
| 核心流程中断 | 登录失败、下单失败 | P0 |
| 功能降级 | 非核心功能失效 | P1 |
| UI/体验问题 | 样式错位、动画异常 | P2 |
| 边缘情况 | 空输入、极大值 | P2 |

### 3. 测试是活的：需要维护

- 当你发现一个 bug，先写一个能复现它的测试，再修 bug
- 当你重构了一段代码，确保测试仍然通过
- 当需求变更，检查并更新相关测试

## 二、测试分层模型

```
┌─────────────────────────────────┐
│         E2E（少量关键路径）        │  5-10 个
└────────────────┬────────────────┘
                 │ 跨系统真实调用
┌────────────────▼────────────────┐
│        集成测试（API + DB）       │  每个 API 路由 3-5 个场景
└────────────────┬────────────────┘
                 │ 模块间交互
┌────────────────▼────────────────┐
│         单元测试（多而快）         │  每个核心函数/类 3-10 个用例
└─────────────────────────────────┘
```

### 各层职责

| 层级 | 数量 | 作用 | 运行速度 |
|------|------|------|---------|
| E2E | 少（5-10个） | 验证真实用户流程 | 慢（秒级） |
| 集成 | 中（覆盖所有 API） | 验证模块间协作 | 中（百毫秒级） |
| 单元 | 多（按需） | 验证单个函数逻辑 | 快（毫秒级） |

## 三、优先级矩阵：测什么

### 3.1 必须测的（P0）

| 场景 | 理由 | 测试类型 |
|------|------|---------|
| **API 路由** | 所有外部入口，错误直接暴露给用户 | 集成 |
| **数据库读写** | 数据丢失是灾难性的 | 集成 |
| **权限/认证逻辑** | 安全漏洞比功能 bug 更严重 | 单元 + 集成 |
| **支付/计费相关** | 金钱问题无小事 | 单元 + 集成 + E2E |
| **核心业务流程** | 业务核心链路不能断 | E2E |

### 3.2 应该测的（P1）

| 场景 | 理由 | 测试类型 |
|------|------|---------|
| **数据转换/解析** | 格式错误传播难发现 | 单元 |
| **配置校验** | 错误配置导致隐性 bug | 单元 |
| **状态机/状态流转** | 状态错乱是常见问题 | 单元 |
| **重试/容错逻辑** | 网络不稳定是常态 | 单元 |
| **事件总线/消息传递** | 模块间通信故障难排查 | 集成 |

### 3.3 可以不测的（P2）

| 场景 | 理由 |
|------|------|
| **简单工具函数** | `formatDate()`、`isEmpty()` 等无需测试 |
| **纯 UI 渲染** | Vue/React 组件由 E2E 覆盖即可 |
| **第三方库本身** | 信任第三方库的质量 |
| **getter/setter** | 无业务逻辑的属性访问无需测试 |
| **边缘情况组合** | 3 个以上边缘条件的组合，爆炸性多，只测最常见的 |

### 3.4 决策流程

```
拿到一个需求/函数 → 问自己：
1. 这个坏了会导致什么？（数据丢失？流程中断？用户体验问题？）
2. 这个问题能被上层测试发现吗？
   - 能 → 交给上层测
   - 不能 → 必须写单元测试
```

## 四、各层测试怎么写

### 4.1 单元测试

**测试对象**：纯函数、类、状态机、配置校验

**原则**：
- 不依赖外部系统（数据库、网络、文件系统）
- 同一函数/类的测试放在一起
- 每个测试只验证一个行为

**示例结构**：
```typescript
describe('MyClass', () => {
  describe('methodName', () => {
    it('should do X when Y', () => { ... });
    it('should throw error when Z', () => { ... });
    it('should return empty array when input is null', () => { ... });
  });
});
```

**Mock 原则**：
- 只 mock 你直接依赖的东西
- 不要 mock 间接依赖（那是集成测试的事）
- 数据库、网络 → 单元测试里必须 mock

### 4.2 集成测试

**测试对象**：API 路由、数据库操作、模块间交互

**原则**：
- 使用真实数据库（用测试库或内存数据库）
- 不 mock 数据库
- 网络调用 → 可以 mock 或用 test double

**API 测试模板**：
```typescript
describe('POST /api/zones', () => {
  it('should create zone and return 201', async () => {
    const res = await request(app)
      .post('/api/zones')
      .send({ title: 'Test Zone', projectId: 'proj-1' })
      .expect(201);

    expect(res.body.zoneId).toBeDefined();
    expect(await db.query('SELECT * FROM zones')).toHaveLength(1);
  });

  it('should return 400 when title is missing', async () => {
    await request(app)
      .post('/api/zones')
      .send({ projectId: 'proj-1' })
      .expect(400);
  });
});
```

### 4.3 E2E 测试

**测试对象**：真实用户流程

**原则**：
- 只测关键路径（happy path + 1-2 个错误路径）
- 不测边缘情况（那是单元测试的事）
- 每个测试独立，不依赖其他测试的执行顺序

**关键流程参考**：

| 系统类型 | 必测流程 |
|---------|---------|
| 有用户系统 | 登录 → 核心操作 → 登出 |
| 有 CRUD | 创建 → 读取 → 更新 → 删除 |
| 有支付 | 下单 → 支付 → 回调 → 查单 |
| 有消息系统 | 发消息 → 收消息 → 消息列表 |
| 有文件上传 | 上传 → 存储 → 下载/删除 |

## 五、测试代码规范

### 5.1 命名

```typescript
// ✅ 描述性的测试名
it('should return 404 when zone does not exist', () => { ... });
it('should create zone with members when all agents are valid', () => { ... });

// ❌ 无意义的命名
it('test 1', () => { ... });
it('works', () => { ... });
```

### 5.2 Arrange-Act-Assert

```typescript
// ✅ 清晰的 AAA 结构
it('should decrease stock when order is placed', async () => {
  // Arrange
  const initialStock = await getStock('product-1');
  const order = createOrder({ productId: 'product-1', quantity: 2 });

  // Act
  await placeOrder(order);

  // Assert
  const newStock = await getStock('product-1');
  expect(newStock).toBe(initialStock - 2);
});

// ❌ Act 和 Assert 混在一起
it('should work', async () => {
  const result = await doSomething();
  expect(result).toBe(expected);
});
```

### 5.3 不要过度断言

```typescript
// ✅ 只断言关键结果
it('should create user with correct email', async () => {
  const user = await createUser({ email: 'test@example.com' });
  expect(user.email).toBe('test@example.com');
  // 不需要断言 id/createdAt 等无关字段
});

// ❌ 断言太多无关内容
it('should create user', async () => {
  const user = await createUser({ ... });
  expect(user.id).toBeDefined();
  expect(user.email).toBe('test@example.com');
  expect(user.createdAt).toBeInstanceOf(Date);
  expect(user.updatedAt).toBeInstanceOf(Date);
  expect(user.status).toBe('active');
  // ... 10+ assertions
});
```

### 5.4 错误测试

```typescript
// ✅ 测试错误也要写
it('should throw ValidationError when email is invalid', async () => {
  await expect(createUser({ email: 'not-an-email' }))
    .rejects.toThrow(ValidationError);
});

// ✅ 测试错误码/错误信息
it('should include error code in response', async () => {
  try {
    await createUser({ email: 'invalid' });
    fail('should have thrown');
  } catch (err) {
    expect(err.code).toBe('INVALID_EMAIL');
  }
});
```

## 六、何时 Mock，何时用真

| 依赖 | 单元测试 | 集成测试 | E2E |
|------|---------|---------|-----|
| 数据库 | ❌ Mock | ✅ 真（测试库） | ✅ 真 |
| 第三方 API | ✅ Mock | ⚠️ 可以 mock | ✅ 真 |
| 文件系统 | ⚠️ Mock | ❌ Mock | ✅ 真（测试目录） |
| 其他内部模块 | ❌ Mock | ✅ 真实调用 | ✅ 真 |
| 时间/日期 | ✅ Mock | ✅ Mock | ⚠️ 真 |

**原则**：越外层越用真，越内层越要隔离。

## 七、发现 bug 后怎么做

```
发现 bug
  ↓
写一个能复现 bug 的测试（此时测试应该 FAIL）
  ↓
修 bug
  ↓
运行测试，验证通过（此时测试应该 PASS）
  ↓
完成
```

**禁止**：先修 bug，再补测试（容易补出假的测试）。

## 八、CI 集成

每个 PR 必须通过：

```yaml
# .github/workflows/test.yml 概要
- run: npm test        # 单元 + 集成
- run: npm run lint    # 代码风格
- run: npm run typecheck # 类型检查
```

E2E 测试可以放在单独的 job 或只在 main 分支跑。

## 九、快速检查清单

拿到一个模块/函数时，问：

```
[ ] 这个模块/函数，坏了会导致什么问题？
[ ] 这个问题被现有测试覆盖了吗？
[ ] 如果没覆盖，我应该写什么测试？
[ ] 这个测试属于单元/集成/E2E 哪一层？
[ ] 我 mock 的是正确的依赖吗？
```

## 十、反模式（不要这样做）

| 反模式 | 问题 |
|-------|------|
| 测试里 sleep 等待异步 | 不稳定，应该用 retry 或 proper await |
| 测试依赖执行顺序 | 测试应该互相独立 |
| 只测 happy path | 错误路径是 bug 高发区 |
| mock 了所有东西 | 变成了在测试 mock，不是在测代码 |
| 测试里写死时间 | `new Date()` 难以测试，应该注入 |
| 大量 beforeEach 共享状态 | 可能导致测试间隐式耦合 |
| 测试不写注释 | 复杂测试逻辑需要说明为什么 |
