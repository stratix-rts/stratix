# DESIGN-asset-pipelines.md — 资产管线总纲（特效 / 角色）

> 状态：已确认（2026-11-06 07:35-07:37 用户拍板）。
> 三条管线**互不共享代码路径**；运行时一律只读整图（GPU 合成），零逐像素主线程成本。

## 0. 总纲

| 管线 | 生成器 | 烘焙时机 | 产物去处 | 触发方 |
|---|---|---|---|---|
| **战场特效** | pixelfx（MIT，vendor 进仓） | **build 期**（发布烘焙；dev 期动态渲染） | 仓库资产（构建期现烘，不入库提交） | 构建链 |
| **角色立绘** | CharacterComposer | **用户期**（首次导入选皮肤 / 更改皮肤） | 用户本地缓存目录（带版本键） | 导入/换肤流程 |
| **UI/皮肤 token** | 既有双 token 体系 | 不烘焙 | — | — |

**铁则：两条烘焙管线禁止互卷**——pixelfx 烘焙链不得 import CharacterComposer 及其部件库；角色合成链不得 import pixelfx。参数面互不借用（特效调色板走 fx-palette token，角色外观走 Composer 自己的模板变量）。

## 1. 特效管线（pixelfx）

### 1.1 形态

- **vendor 进仓**：pixelfx 源码进 `vendor/pixelfx/`（MIT，保留 LICENSE/NOTICE.md）；vite 别名从仓外兄弟目录改指仓内；删 `server.fs.allow` 特例。
- **dev**：代码路由动态渲染（现有 dev 入口 `fx-code-dev.html` 保持），改特效代码即刻可见。
- **release**：构建期烘焙 sheet（含**按特效调色板变体**，皮肤为 build 期闭集 modern/pixel）；运行时只读 atlas。
- **参数面翻译表**（运行时参数 → 烘焙表达）：`palette` → 按皮肤烘变体；`flip` → GPU `setFlipX`（免费，不烘 N 张）；`angle` → 离散方向烘 N 桶或收敛到镜像；`seed` → 烘 K 变体随机选。超出此面的效果标 `runtime-only`，dev/prod 都走代码路由，护栏照旧（并发 2 + 面积 ≤40,960px + 降频 + 挤实例）。

### 1.2 三条硬约束

1. **烘焙确定性**：同输入必同输出（seed 钉死；构建可重现）。
2. **双路由像素一致性测试**：同一效果 code-route 现算帧 vs 烘焙帧，采样 t 点逐像素 diff（容差内），进 CI。漂移当场报警，烘焙资产不提交入库。
3. **分流判据**沿用 `docs/research/pixelfx-runtime-poc.md` §5.1 三条：要运行时变体吗 / 面积 ≤40,960px / 同屏 ≤2 条。

### 1.3 生产接线（补 162 §5.3 前置条件）

`CodeFxLayer` 挂进 `BattlefieldScene`；pixelfx 加载失败/效果缺失 ⇒ **静默回落 sheet 路由**；`prefers-reduced-motion` ⇒ 不播代码路由（沿用 `world/motion.ts` 口径）。

## 2. 角色管线（CharacterComposer）

### 2.1 触发与产物

- **触发**：①用户首次导入 Agent 并选择皮肤 ②用户更改皮肤。两处都在导入/设置流程内，烘焙成本藏进等待。
- **产物**：部件合成**一张整精灵图** + atlas 元数据，存**用户本地缓存目录**（app userData 侧），不进仓库、不进 `.stratix` 契约目录。

### 2.2 三条纪律

1. **缓存键 = agent 标识 + 皮肤 + Composer 版本号**。Composer 逻辑/部件素材升级 ⇒ 版本变 ⇒ 旧图自动失效重烘。无此键，composer bug 会烤进缓存永久存活。
2. **静默降级，用户无感知**（2026-11-06 07:37 用户拍板）：烘焙失败 ⇒ 自动回落运行时直接合成（现状路径），用户永远看到可用结果；失败**只进内部日志/遥测**，不弹错不阻塞。修 bug 保证生成无误是**我们的职责**，不是用户的。
3. **本地缓存可整体重建**：删缓存目录 ⇒ 下次触发时点全量重烘，无其他依赖。

### 2.3 边界

- 眼睛层 URL 模板变量未插值的已知 bug：在烘焙管线落地时一并修复（烘焙期的静默日志会暴露全部此类问题，逐个归零）。

## 3. 收单纪律（两遍确认，全任务生效）

1. **第一遍（worker 自验）**：按任务【验证方式】跑 typecheck + 相关 jest，输出原样贴出。
2. **第二遍（调度者粗检）**：收单时独立重跑 typecheck + 相关目录测试 + diff 抽查（重点：禁止事项条款、选择性 git add、无范围外文件混入）。两遍都过才算收单。
