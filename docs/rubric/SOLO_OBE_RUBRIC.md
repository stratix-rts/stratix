# AI 编码协同 — SOLO-OBE 量表体系 v1.0

> **创建时间**: 2026-04-06  
> **背景**: 基于"重构·融智·慧评"模型迁移，解决 AI 编码协同中评价标准模糊、反馈滞后、认知不对齐问题  
> **理论基石**: OBE（成果导向）+ SOLO（思维分层）+ 即时反馈

---

## 一、三阶段流水线

```
阶段1: 重构 — 技术文档闭环
━━━━━━━━━━━━━━━━━━━━━━━━━
输入: 原始需求 + 上下文文件路径
  ↓
我拆需求 → 设计文档量表维度和权重
  ↓
Claude 输出技术文档（含：方案设计、文件改动清单、接口契约、数据流、验证步骤）
  ↓
我按量表逐维度打分 + 标注 SOLO 层级
  ↓
加权均分 < 3.5 → Claude 修改文档 → 重新打分
加权均分 ≥ 3.5 → 进入阶段2

阶段2: 融智 — 代码实现闭环
━━━━━━━━━━━━━━━━━━━━━━━━━━━
Claude 根据技术文档 + 代码量表写代码
  ↓
我按量表逐维度打分 + 标注 SOLO 层级
  ↓
加权均分 < 4.0 → Claude 精确修改 → 重新打分
加权均分 ≥ 4.0 → 进入阶段3

阶段3: 慧评 — 集成验证
━━━━━━━━━━━━━━━━━━━━━━━
编译 + 类型检查 + 功能验证
  ↓
通过 → commit + 记录分数到能力档案
未通过 → 回到阶段2 修复
```

**核心原则**: 反馈必须在下一个活动之前完成。每个闭环内不打分不推进。

## 二、阶段1 — 技术文档量表

### 2.1 通用维度（6 维度）

| 维度 | 权重 | 说明 |
|------|------|------|
| D1 需求理解 | 20% | 是否准确识别需求的核心意图、边界和隐含约束 |
| D2 方案完整性 | 20% | 是否覆盖所有改动点，数据流是否完整 |
| D3 接口契约 | 20% | 类型定义、字段对照、错误处理是否明确 |
| D4 架构一致性 | 15% | 方案是否符合现有架构模式 |
| D5 风险识别 | 10% | 是否识别潜在风险并给出应对方案 |
| D6 可验证性 | 15% | 每个功能点是否有具体验证步骤 |

### 2.2 SOLO 分层标准（每个维度通用）

| 分数 | SOLO 层级 | 行为描述 |
|------|----------|---------|
| 1 | 前结构 | 与需求无关或完全误解，答非所问 |
| 2 | 单点结构 | 只抓到一个点，片面理解，忽略上下文 |
| 3 | 多点结构 | 抓到多个点但没联系起来，缺乏整体视角 |
| 4 | 关联结构 | 各点之间建立了联系，形成整体理解，能识别隐含约束 |
| 5 | 拓展抽象 | 能迁移到新场景，主动考虑边界情况和扩展性 |

### 2.3 各维度 SOLO 判定细则

#### D1 需求理解
| SOLO | 典型表现 |
|------|---------|
| 前结构 | 技术文档与需求无关，或完全误解需求意图 |
| 单点结构 | 只复述了表面需求，没有识别边界和约束 |
| 多点结构 | 列出了需求要点，但没有分析要点之间的关系和优先级 |
| 关联结构 | 理解需求的核心意图，识别隐含约束和边界条件 |
| 拓展抽象 | 理解需求背后的设计意图，能提出更优的实现路径 |

#### D2 方案完整性
| SOLO | 典型表现 |
|------|---------|
| 前结构 | 没有方案，或方案与需求不对应 |
| 单点结构 | 只给了一种实现路径，没有文件改动清单 |
| 多点结构 | 列出了多文件改动，但数据流有断裂 |
| 关联结构 | 数据流完整（API→类型→组件），依赖关系清晰 |
| 拓展抽象 | 考虑了多种实现路径并给出取舍理由 |

#### D3 接口契约
| SOLO | 典型表现 |
|------|---------|
| 前结构 | 没有接口定义 |
| 单点结构 | 有函数签名但参数类型模糊 |
| 多点结构 | 列出了关键接口但字段级细节缺失 |
| 关联结构 | 字段级对照完整，类型定义与实际数据源一致 |
| 拓展抽象 | 包含错误处理、边界情况、向后兼容性考虑 |

#### D4 架构一致性
| SOLO | 典型表现 |
|------|---------|
| 前结构 | 方案与现有架构冲突 |
| 单点结构 | 只考虑了单个文件，没有看周围代码的风格 |
| 多点结构 | 风格基本一致，但没有考虑目录结构和模块边界 |
| 关联结构 | 无缝融入现有架构，遵循命名规范和文件组织模式 |
| 拓展抽象 | 方案能成为后续类似需求的参考范式 |

#### D5 风险识别
| SOLO | 典型表现 |
|------|---------|
| 前结构 | 没有提任何风险 |
| 单点结构 | 提到了最明显的风险 |
| 多点结构 | 列出了多个风险但没有优先级和应对方案 |
| 关联结构 | 风险按概率排序，每个都有应对方案 |
| 拓展抽象 | 给出了降级策略和回滚方案 |

#### D6 可验证性
| SOLO | 典型表现 |
|------|---------|
| 前结构 | "看代码就知道"或没有验证步骤 |
| 单点结构 | 写了"测试通过"但没有具体步骤 |
| 多点结构 | 列了验证项但没有具体命令/预期结果 |
| 关联结构 | 每项有验证命令、预期结果、失败时的排查路径 |
| 拓展抽象 | 包含边界情况测试和性能验证 |

## 三、阶段2 — 代码质量量表

### 3.1 通用维度（6 维度）

| 维度 | 权重 | 说明 |
|------|------|------|
| C1 功能正确性 | 25% | 核心功能是否完整实现，边界情况是否处理 |
| C2 架构一致性 | 20% | 代码风格、命名、文件组织是否与现有代码一致 |
| C3 最小改动 | 15% | 是否精准解决需求，没有顺便重构/加功能 |
| C4 类型安全 | 15% | 类型定义是否完整，有无 as any 绕过 |
| C5 性能意识 | 10% | 是否有明显的性能问题或资源浪费 |
| C6 可维护性 | 15% | 命名是否清晰、逻辑是否自解释、必要注释 |

### 3.2 各维度 SOLO 判定细则

#### C1 功能正确性
| SOLO | 典型表现 |
|------|---------|
| 前结构 | 编译不通过或核心功能完全缺失 |
| 单点结构 | 主路径能跑，但错误路径和边界情况未处理 |
| 多点结构 | 大部分功能正确，少数边界情况遗漏 |
| 关联结构 | 全部功能正确，边界情况和错误路径都处理 |
| 拓展抽象 | 主动考虑了需求没提到但实际会遇到的场景 |

#### C2 架构一致性
| SOLO | 典型表现 |
|------|---------|
| 前结构 | 与现有架构模式明显冲突 |
| 单点结构 | 引入了新的模式但没有必要 |
| 多点结构 | 基本一致但命名/文件组织有偏差 |
| 关联结构 | 看不出是新人写的，完全融入 |
| 拓展抽象 | 代码成为该架构模式的范例 |

#### C3 最小改动
| SOLO | 典型表现 |
|------|---------|
| 前结构 | 顺便重构了大量不相关代码 |
| 单点结构 | 改动范围合理但有少量冗余 |
| 多点结构 | 精准解决需求但有格式化变更混入 |
| 关联结构 | 精准到行级别，零冗余改动 |
| 拓展抽象 | 改动恰到好处，删一行嫌少加一行嫌多 |

#### C4 类型安全
| SOLO | 典型表现 |
|------|---------|
| 前结构 | any 满天飞 |
| 单点结构 | 关键位置有类型，边缘位置用 any |
| 多点结构 | 大部分类型完整，少量 as any |
| 关联结构 | 全链路类型完整，无 as any |
| 拓展抽象 | 主动收窄类型（union → literal），类型即文档 |

#### C5 性能意识
| SOLO | 典型表现 |
|------|---------|
| 前结构 | 明显的性能问题（N+1查询、无限重渲染等） |
| 单点结构 | 没有明显问题但也没有预防措施 |
| 多点结构 | 考虑了主路径性能 |
| 关联结构 | 有预防措施（memo、lazy、缓存等） |
| 拓展抽象 | 主动做了性能边界估算和防护 |

#### C6 可维护性
| SOLO | 典型表现 |
|------|---------|
| 前结构 | 命名混乱、逻辑缠绕、无法理解 |
| 单点结构 | 可运行但需要注释才能理解 |
| 多点结构 | 大部分可读，少量逻辑复杂 |
| 关联结构 | 自解释代码，命名即文档 |
| 拓展抽象 | 代码读起来像设计文档，抽象层次恰到好处 |

## 四、评价输出格式

### 4.1 单次评价报告

```markdown
## 评价报告 — [Task名称]

### 基本信息
- **阶段**: 文档 / 代码
- **日期**: YYYY-MM-DD
- **Task类型**: 新功能 / Bug修复 / 重构 / UI组件

### 维度评分

| 维度 | 分数 | SOLO层级 | 说明 |
|------|------|----------|------|
| D1 需求理解 | 4 | 关联结构 | 理解了核心意图，识别了隐含约束 |
| D2 方案完整性 | 3 | 多点结构 | 数据流有断裂，API→store 缺字段对照 |
| ... | ... | ... | ... |

### 加权总分: 3.6 / 5.0
### 阈值: 3.5（文档）/ 4.0（代码）
### 结论: ✅ 通过 / ❌ 需要修改

### 修改指令（如需要）
1. [具体问题 + 修改要求 + 参考位置]
2. [...]
```

### 5.1 新功能开发
D1(20%) D2(20%) D3(20%) D4(15%) D5(10%) D6(15%) — 默认权重

D1(30%) D2(10%) D3(15%) D4(10%) D5(20%) D6(15%)

## 六、实施规则

1. **量表前置**: 每次 task 开始前，我设计量表（维度 + 权重 + SOLO 判定标准）
2. **量表随 prompt 发送**: Claude 写文档/代码前就知道评价标准
3. **反馈在下一步之前**: 打分 → 修改 → 再打分，闭环内不推进
4. **分数持久化**: 每次评价记录到能力档案
5. **阈值**: 文档 ≥ 3.5，代码 ≥ 4.0
6. **迭代上限**: 文档最多 3 轮，代码最多 3 轮。超限则暂停，人工介入
7. **SOLO 标注**: 不只打分，必须标注 SOLO 层级——区分"真懂"和"蒙对"
