# 需求设计量表 (Requirements Rubric)

> 用于评价每个 task prompt 的**需求质量**，在写 prompt 之前自检。

## 评分维度

```
R1-R5 每项 1-5 分，加权总分 = Σ(分数 × 权重)
 / 5
```

### R1: 来源可追溯 (权重 20%)

需求中的每一个 Props/Emits/类型定义，是否能追溯到 V1 源码或 App.vue 调用方？

| 分数 | 含义 |
|------|------|
| 5 | 每个字段都有 V1 源码行号引用或 App.vue 调用对照 |
| 4 | 大部分有来源，个别字段是推断的（但标注了"推断"） |
| 3 | 一半有来源，一半是猜测 |
| 2 | 大部分是凭空设计的，没有对照 V1 |
| 1 | 完全凭空设计 |

**检查方法**：在写 Props 时，确认 `grep -n "editCharacterId\|@created\|@updated" App.vue` 匹配。

### R2: 必要性验证 (权重 25%)
这个组件/功能在 V1 中**真的存在**吗？还是你凭空加的？

| 分数 | 含义 |
|------|------|
| 5 | V1 中有明确对应的组件/功能 |
| 4 | V1 有类似功能，V4 合理扩展 |
| 3 | V1 没有但系统确实需要 |
| 2 | 可有可无，去掉不影响系统完整性 |
| 1 | 完全不需要、凭空造的 |

**检查方法**：搜索 V1 源码确认组件是否存在。

### R3: 接口真实性 (权重 25%)
Props/Emits 的字段名和类型是否与**实际调用方**一致？

| 分数 | 含义 |
|------|------|
| 5 | 与 App.vue + V1 完全对齐 |
| 4 | 基本对齐，缺省值合理 |
| 3 | 接口名不同但类型兼容 |
| 2 | 接口不兼容，需要适配层 |
| 1 | 接口完全对不上 |

**检查方法**：`grep -A5 "CharacterCreatorModal" App.vue` 对照 defineProps。

### R4: 完整性 (权重 15%)
需求描述是否足够 Claude 理解**做什么**和**不做什么**？

| 分数 | 含义 |
|------|------|
| 5 | 任务+上下文+验收标准+禁止事项全覆盖，无歧义 |
| 4 | 基本完整，小细节可能需要 Claude 自行判断 |
| 3 | 缺少部分上下文，Claude 可能猜错 |
| 2 | 描述模糊，Claude 大概率理解偏差 |
| 1 | 只说了"做个 X"，其他全靠猜 |

### R5: 最小范围 (权重 15%)
需求是否控制了组件的边界，没有过度膨胀？

| 分数 | 含义 |
|------|------|
| 5 | 精确描述单个组件的职责，没有多余功能 |
| 4 | 基本精确，有少量可接受的扩展 |
| 3 | 职责边界模糊，可能产出过大 |
| 2 | 描述了一个大杂烩组件 |
| 1 | 需求本身就是"做一个完整的XX系统" |

## 使用方式

写每个 task prompt **之前**，用这个量表自检：

```
1. R1: 这个组件在 V1 里有吗？ → 搜索 V1 源码确认
2. R2: App.vue 怎么调用它的？ → grep App.vue 对照接口
3. R3: Props/Emits 名字对得上吗？ → 逐字段确认
4. R4: 描述够清楚吗？ → 给别人看能不能理解
5. R5: 是不是只做一件事？ → 职责是否单一

加权总分 < 3.0 → 重新设计需求
加权总分 3.0-4.0 → 补充后重评
加权总分 ≥ 4.0 → 可以发出
```
