# Character Creator V4 — 任务专属量表

> **创建时间**: 2026-04-08
> **基于**: V3 量表 + A1-A8 美学约束（基于 Ngo, Teo, Byrne 2000）  
> **任务类型**: UI 组件重写（Vue 为主 + Phaser 仅 Canvas）  
> **评价依据**: SOLO-OBE 体系（见 `SOLO_OBE_RUBRIC.md`）  
> **背景**: 从 V1（Phaser 为主的 1539 行 Scene + 7774 行 UI）翻转为 Vue 为主架构。core/ 不动。

## 三、美学质量量表（A1-A8）— V4 新增

> **基于**: Ngo, Teo, Byrne (2000) "Modelling Interface Aesthetics" 14 项美学指标
> **用途**: 作为 prompt 约束注入 LLM，评估 UI 代码的视觉质量
> **详细规则**: 见 `docs/AESTHETIC_CONSTRAINTS.md`

| 维度 | 权重 | 说明 | Ngo 来源 |
|------|------|------|----------|
| A1 间距规律性 | 15% | 间距使用 token，同层一致，外大内小 | Regularity + Rhythm |
| A2 布局对齐 | 15% | flex/grid 布局，对齐属性显式声明 | Balance + Equilibrium |
| A3 色彩与风格统一 | 20% | 颜色用 CSS 变量，同类统一，主色 ≤ 3 种 | Unity + Homogeneity |
| A4 比例与尺寸 | 10% | 经典比例，同类等尺寸，8px 基准 | Proportion + Cohesion |
| A5 视觉层级与阅读流 | 20% | 3 层字号，1 个焦点，阅读流合理 | Sequence + Order |
| A6 简洁性 | 10% | 选择器 ≤ 3 层，属性 ≤ 15 条，无重复 | Simplicity + Economy |
| A7 信息密度 | 5% | 留白 30-50%，分组明显 | Density |
| A8 对称与结构 | 5% | 对称默认，非对称需理由 | Symmetry |

**美学阈值**: 加权均分 ≥ 3.5 通过

### A1-A8 SOLO 判定细则

#### A1 间距规律性
| SOLO | 表现 |
|------|------|
| 前结构 | 无间距系统，全硬编码随意数值 |
| 单点结构 | 有间距概念但大量硬编码（>30%） |
| 多点结构 | 大部分用 token，偶尔硬编码（<10%） |
| 关联结构 | 全部使用 token，间距一致，外大内小递进 |
| 拓展抽象 | 间距有节奏设计，且能解释节奏选择理由 |

#### A2 布局对齐
| SOLO | 表现 |
|------|------|
| 前结构 | 无统一布局策略，绝对定位做正常布局 |
| 单点结构 | 用了 flex/grid 但缺少显式对齐 |
| 多点结构 | 大部分容器有对齐，偶尔遗漏 |
| 关联结构 | 布局策略统一，对齐属性完整，响应式适配 |
| 拓展抽象 | 布局系统可复用到其他组件 |

#### A3 色彩与风格统一
| SOLO | 表现 |
|------|------|
| 前结构 | 全硬编码色值，同类元素样式不一致 |
| 单点结构 | 部分用 CSS 变量，大量硬编码 |
| 多点结构 | 有 token 系统但偶尔硬编码（<5 处） |
| 关联结构 | 完整 token 系统，同类元素完全一致 |
| 拓展抽象 | token 系统成为项目的设计语言基础 |

#### A4 比例与尺寸
| SOLO | 表现 |
|------|------|
| 前结构 | 随意尺寸，无比例考量 |
| 单点结构 | 有尺寸概念但无比例意识 |
| 多点结构 | 部分容器有比例，同类基本统一 |
| 关联结构 | 关键容器有经典比例，同类统一 |
| 拓展抽象 | 比例有设计意图，响应式下保持 |

#### A5 视觉层级与阅读流
| SOLO | 表现 |
|------|------|
| 前结构 | 无视觉层级，所有文字一样重要 |
| 单点结构 | 有大小区分但无系统层级 |
| 多点结构 | 有层级概念但层级过多或焦点不唯一 |
| 关联结构 | 3 层以内，焦点明确，阅读流合理 |
| 拓展抽象 | 层级设计有决策理由，可复用 |

#### A6 简洁性
| SOLO | 表现 |
|------|------|
| 前结构 | 深度嵌套选择器，大量重复样式 |
| 单点结构 | 有简洁意识但选择器偏深或重复多 |
| 多点结构 | 大部分简洁，少量冗余 |
| 关联结构 | 选择器 ≤ 3 层，零重复，无死代码 |
| 拓展抽象 | 每个样式有存在理由说明 |

#### A7 信息密度
| SOLO | 表现 |
|------|------|
| 前结构 | 内容堆砌或过度留白 |
| 单点结构 | 有留白意识但密度不均 |
| 多点结构 | 密度基本合理但个别区域偏密 |
| 关联结构 | 密度匹配页面类型，分组清晰 |
| 拓展抽象 | 密度设计有用户认知负荷考量 |

#### A8 对称与结构
| SOLO | 表现 |
|------|------|
| 前结构 | 无结构对称意识 |
| 单点结构 | 有结构意识但不统一 |
| 多点结构 | 大部分对称，偶尔不一致 |
| 关联结构 | 对称一致，非对称有功能性理由 |
| 拓展抽象 | 结构设计成为视觉语言的一部分 |

## 五、与 V3 的对比设计

V3 和 V4 使用相同的：
- 原始需求文档（`docs/CHARACTER_CREATOR_V2_REDESIGN.md`）
- 技术规格（CC_V4_TECH_SPEC.md，内容与 V3 一致）
- Task 拆解（CC_V4_TASKS.md，18 个 task）
- 需求设计量表（R1-R5）
- 代码质量量表（C1-C6）

V4 唯一增量：
- **A1-A8 美学约束**注入每个 task prompt
- **C 系列评分 + A 系列评分**双量表独立打分

对比维度：
| 对比项 | V3 | V4 | 变量 |
|--------|----|----|------|
| C 系列总分 | ? | ? | 美学约束是否影响代码质量 |
| A 系列总分 | ? | ? | 美学约束的增量效果 |
| tsc 错误数 | 0 | ? | 美学约束是否影响编译正确性 |

### C1 功能正确性 — V1 行为对照

| SOLO | V4 重写中的表现 |
|------|----------------|
| 前结构 | 组件不能渲染或编译不通过 |
| 单点结构 | 能显示但交互不工作（点击/选择无反应） |
| 多点结构 | 主功能可用但边界情况缺失（空数据、切换体型后状态不一致） |
| 关联结构 | 所有功能与 V1 行为一致，包括错误处理和边界情况 |
| 拓展抽象 | 主动考虑 V1 没处理但应该处理的场景（如组件卸载时清理 Phaser） |

### C2 架构一致性 — Vue 为主模式

| SOLO | 表现 |
|------|------|
| 前结构 | 在 Vue 组件里直接操作 Phaser 全局状态 |
| 单点结构 | Phaser 用法正确但目录结构不符合 v4/ 规范 |
| 多点结构 | 结构正确但 composables 和组件的职责划分不清 |
| 关联结构 | 严格遵循 Vue 为主 + Phaser 仅在 CanvasPreview 中的约束 |
| 拓展抽象 | composable 抽象层设计成为后续类似迁移的参考范式 |

### C3 最小改动 — core/ 不动原则

| SOLO | 表现 |
|------|------|
| 前结构 | 修改了 core/ 下的文件 |
| 单点结构 | 没改 core/ 但引入了不必要的第三方依赖 |
| 多点结构 | 改动合理但混入了与当前 task 无关的格式化/重命名 |
| 关联结构 | 精准只改 task 范围内的文件，core/ 完全不动 |
| 拓展抽象 | 改动恰到好处，每个文件的改动都有明确理由 |

### C4 类型安全 — V1→V4 类型桥接

| SOLO | 表现 |
|------|------|
| 前结构 | `any` 满天飞，没有类型定义 |
| 单点结构 | 有基本类型但 composable 返回值无类型 |
| 多点结构 | 大部分有类型但 props/emits 定义不完整 |
| 关联结构 | 完整的 TypeScript 类型链：core 类型 → composable → 组件 props |
| 拓展抽象 | 主动收窄类型，用 discriminated union 代替宽泛类型 |

### C5 性能意识 — Phaser 生命周期

| SOLO | 表现 |
|------|------|
| 前结构 | Phaser Game 不销毁，事件监听器不清理 |
| 单点结构 | 有 onUnmounted 但只销毁 Game 不清定时器 |
| 多点结构 | 基本清理完整但 deep watch 导致不必要的重渲染 |
| 关联结构 | Phaser 生命周期完整管理，watch 精确，无内存泄漏 |
| 拓展抽象 | 主动做了防抖/节流处理，避免高频 props 变化触发重渲染 |

### C6 可维护性 — 组件职责单一

| SOLO | 表现 |
|------|------|
| 前结构 | 一个文件混合 UI + 状态 + 业务逻辑 |
| 单点结构 | 拆了组件但 composable 返回 20+ 个函数 |
| 多点结构 | 职责基本清晰但命名不一致（中英混用） |
| 关联结构 | 每个组件/composable 职责单一，命名一致 |
| 拓展抽象 | 组件接口设计清晰到可以作为文档使用 |
