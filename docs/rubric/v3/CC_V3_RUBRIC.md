## 三、V3 特有的 SOLO 判定细则

### C1 功能正确性 — V1 行为对照

| SOLO | V3 重写中的表现 |
|------|----------------|
| 前结构 | 组件不能渲染或编译不通过 |
| 单点结构 | 能显示但交互不工作（点击/选择无反应） |
| 多点结构 | 主功能可用但边界情况缺失（空数据、切换体型后状态不一致） |
| 关联结构 | 所有功能与 V1 行为一致，包括错误处理和边界情况 |
| 拓展抽象 | 主动考虑 V1 没处理但应该处理的场景（如组件卸载时清理 Phaser） |

### C2 架构一致性 — Vue 为主模式

| SOLO | 表现 |
|------|------|
| 前结构 | 在 Vue 组件里直接操作 Phaser 全局状态 |
| 单点结构 | Phaser 用法正确但目录结构不符合 v3/ 规范 |
| 多点结构 | 结构正确但 composables 和组件的职责划分不清 |
| 关联结构 | 严格遵循 Vue 为主 + Phaser 仅在 CanvasPreview 中的约束 |
| 拓展抽象 | composable 抽象层设计成为后续类似迁移的参考范式 |

### C3 最小改动 — core/ 不动原则

| SOLO | 表现 |
|------|------|
| 前结构 | 修改了 core/ 下的文件 |
| 单点结构 | 没改 core/ 但引入了不必要的第三方依赖 |
| 多点结构 | 改动合理但混入了与当前 task 无关的格式化/重命名 |
| 关联结构 | 精准只改 task 范围内的文件，core/ 完全不动 |
| 拓展抽象 | 改动恰到好处，每个文件的改动都有明确理由 |

### C4 类型安全 — V1→V3 类型桥接

| SOLO | 表现 |
|------|------|
| 前结构 | `any` 满天飞，没有类型定义 |
| 单点结构 | 有基本类型但 composable 返回值无类型 |
| 多点结构 | 大部分有类型但 props/emits 定义不完整 |
| 关联结构 | 完整的 TypeScript 类型链：core 类型 → composable → 组件 props |
| 拓展抽象 | 主动收窄类型，用 discriminated union 代替宽泛类型 |

### C5 性能意识 — Phaser 生命周期

| SOLO | 表现 |
|------|------|
| 前结构 | Phaser Game 不销毁，事件监听器不清理 |
| 单点结构 | 有 onUnmounted 但只销毁 Game 不清定时器 |
| 多点结构 | 基本清理完整但 deep watch 导致不必要的重渲染 |
| 关联结构 | Phaser 生命周期完整管理，watch 精确，无内存泄漏 |
| 拓展抽象 | 主动做了防抖/节流处理，避免高频 props 变化触发重渲染 |

### C6 可维护性 — 组件职责单一

| SOLO | 表现 |
|------|------|
| 前结构 | 一个文件混合 UI + 状态 + 业务逻辑 |
| 单点结构 | 拆了组件但 composable 返回 20+ 个函数 |
| 多点结构 | 职责基本清晰但命名不一致（中英混用） |
| 关联结构 | 每个组件/composable 职责单一，命名一致 |
| 拓展抽象 | 组件接口设计清晰到可以作为文档使用 |
