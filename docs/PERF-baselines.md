### 1.2 两种「渲染侧形态」

| 形态 | 含义 | 为什么都要量 |
|---|---|---|
| `dev` | **vite dev server**（仓库那份 `vite.config.ts` 原样复用，只换端口/代理目标） | 开发期体感（`npm run dev` 之后多久能看见画面） |
| `prod` | **vite preview 服务生产产物**（`dist/perf-frontend/`，rollup 打完的 bundle） | **用户实际下载/执行的那份代码**（dev 的 273 个模块逐个转译，用户拿不到） |

service 侧与形态无关（两种形态跑的是同一个 service 进程）⇒ §2 只给一张表，并附 prod 形态的独立复现值。

### 1.3 口径定义

- **service 侧**：计时基准 = 驱动脚本自己 spawn 子进程的那一瞬（`Date.now()`）；分段计时基准 = 进程内 `process.uptime()`
  （**必须**用它：node 启动 + tsx 转译发生在模块体之前，`Date.now()` 的基准太晚，量不到）。
- **渲染侧**：页面时钟 `performance.now()`，`navigation start` 为 0 点 ⇒ 与 FCP / DOMContentLoaded 同一把尺。
  - `FCP` = `performance.getEntriesByType('paint')` 里的 `first-contentful-paint`；
  - `首屏` = `strat-lobby-panel` 元素**挂载**时刻（MutationObserver 记录，`document.querySelector` 命中即记）；
  - `战场 scene create` = 场景类的 `create()` **返回之后**打的 `performance.mark`（= 场景建完、层都建好了）。
- **端到端**：起点 = spawn service；终点 = `window.__srfApp.snapshot().activeInstanceId === 'wsp_sandbox'`（**页面可点进沙盒**）。

### 1.4 打点是怎么做的（零产品改动）

「战场 scene create 完成」在产品码里**没有任何可观测点**（world 层零 DOM；Phaser 3.90 的 dist 里没有 `window.PHASER_GAME`；
场景实例也没暴露给页面）⇒ 只能在**构建期注入**：

- 注入发生在**测试侧**（`e2e-tests/perf-baseline/scene-marks.ts`，一个 vite 插件）：
  给 `BattlefieldScene` / `LobbyScene` / `FxAssetScene` 的 `create` 包一层，**多打一条 `performance.mark`**；
- 仓库里的 `src/**` **一个字节都没改** ⇒ 产品路径零行为变化（`tsc` 也绿，见 §7）；
- dev 形态在 dev server 侧注入，prod 形态在**生产构建**侧注入 ⇒ 两个形态用的是同一份注入代码（口径一致）。

**读法**

- service 冷启 = **561ms**，其中 **338ms（60%）是「把代码装进内存」**（node 冷启 + tsx 转译 + 模块求值），

- 561 − 415 = 146ms = 进程 spawn 往返 + 驱动侧 `/health` 首帧轮询 + READY 打印的差；
- **roster 物化不在开机链上**：`materializeInstanceRoster` 对默认沙盒直接 skip（沙盒不误伤），
  它只在**进非沙盒实例**时发生 ⇒ 实测 5ms（见 §4），**不是**开机瓶颈；
- 生产 gateway 比最小复刻多 **405ms**（966 − 561）⇒ 那些额外子系统是后端冷启的**第二根杠杆**（候选 2）。

## 5. 最大段结论

1. **最大段 = service 进程冷启（586ms / 41%）**，而它的内部最大段是**模块装载（338~366ms / service 的 60~62%）**——
   也就是「把代码装进内存」，**不是**业务逻辑。真正不可省的只有 **76ms**（dbInit 51 + branch 13 + boot 5 + listen 7）。
2. **渲染侧（prod）的最大段 = 模块执行 + Phaser 启动（237ms）**，其次是「FCP → 大厅面板挂载」的 242ms（在等数据与卡片渲染）。
3. **dev 与 prod 的差 = 420ms**（战场 scene create 893 → 473）⇒ **「用生产 bundle 而不是 dev server」本身就是最大的单点收益**，
   而它**已经落地**（`npm run build:frontend`），本单只是把它量化。
4. **roster 物化 5ms、DB init 51ms、git 分支探测 13ms** —— 量完就排除了，**都不是**瓶颈。
5. **唯一一处产品语义造成的延迟**：实例切换的可见延迟 = **122ms**，其中 **~100ms 是 world-sync 的 100ms 快照节流**
   （service 侧只花 5ms）⇒ 收益明确、改动面极小（§6 候选 1）。

## 6. 优化候选（本单只分析；候选 1 已由 PERF-02 / task_231 实施，见 §9）

### 候选 1 · world-sync 快照节流 100ms → 25ms（关键事件直发）—— **已实施**（PERF-02 / task_231 ⇒ §9）

| 项 | 内容 |
| --- | --- |
| **定位** | `src/stratix-gateway/api/websocket/world-sync/endpoint.ts:217`（`WORLD_SYNC_SNAPSHOT_THROTTLE_MS = 100`）+ `scheduleBroadcast()`（同文件 524~532 行）。端点已暴露 `snapshotThrottleMs` 选项 ⇒ 改口径不需要改协议、不需要改前端。 |
| **证据** | 点「进入」→ `activeInstanceId` 变更 = **122ms**，其中 service 侧裁决 **5ms** ⇒ **~100ms 是「等节流窗口」**（`scheduleBroadcast` 用 `setTimeout(throttleMs)` 排下一次广播 ⇒ 第一次变更也得等满一窗）。退出副本回大厅同样 **119ms**。 |
| **预期收益量级** | 每次实例切换 / 状态确认的可见延迟 **-75ms**（122 → ~45ms）；端到端「可点进沙盒」**-75ms**（prod 口径 1414ms 的 **5%**）。每次进出副本都省一遍。 |
| **风险** | **中低**。节流窗是防广播风暴的闸；单纯把窗口调到 25ms ⇒ 高频状态事件（`unit.position` 等）的广播频率 ×4。**建议改法**：位置类事件仍走 100ms 合并，只有「实例切换 / `project.changed`」这类**低频但关键**的变更走**立即广播**（首播不等窗口）⇒ 高频路径的广播量完全不变。协议面不变（有回执核对），前端零改动。 |
| **改动面** | **小**：1 个常量 + 端点里 1 条「关键事件直发」旁路（约 20~40 行）+ 1 个单测（节流行为：高频合并仍在、低频关键事件不等窗）。**不碰 core、不碰前端、不碰协议格式**。 |
| **验收口径** | 跑本单脚本（prod 三轮）看「点「进入」→ 生效」是否降到 ~40ms；再跑 QA harness 全量（world-sync 有回执核对，行为面应不变）。 |

### 候选 2 · 后端子系统懒加载 + 渲染侧拆包 / 延后 Phaser —— **独立分支（改动面 ≥3 万行量级）**

| 项 | 内容 |
| --- | --- |

**口径（读数前必读）**

- **字节** = 下行 WS 消息的 **UTF-8 载荷长度**（= 浏览器 `JSON.parse` 之前收到的那份文本）；**不含 WS 帧头**（2~14 B/帧，本单量级下可忽略）。
- **帧** = 一条下行 WS 消息（`snapshot` / `event.push` / `command.ack` / `error`）。
- **上行**（客户端 → service）单独记，**不计入**「广播体积」。
- **场景 A** = 进副本（roster 物化出单位）→ **静默期**（把后台 agent 探测的余波排干净）→ 60s 无任何操作。
- **场景 B** = 与 A **完全相同**的起始状态 → 60s 内两环并行：
  - **交互环 10Hz**（压力口径，远超真人手速）：`click.set` / `move.one` / `box.select` / `hud.select` / `click.add` / `move.formation` 六类轮转；
  - **辅助环 1Hz**：`mission.checkpoint`（任务记账）/ `poll.hello`（重发 hello 拉一份全量 —— 协议里唯一的「拉全量」手段）/ `director.toggle`。
- **按操作归因** = 帧**到达时刻**所处的操作（近似口径：帧比操作晚到几十毫秒，落在同一操作窗内）。
- **相邻帧重复率** = 相邻两帧 `snapshot` 的 JSON 叶子字段（路径级）逐个比对；「只发改动字段的字节」= 变了的那几个**顶层字段**的字节占全量帧字节的比例。

### 10.2 场景 A · 静默挂机 60s

| 指标 | 值 |
|---|---|
| 下行总字节 | **0 B** |
| 下行帧数 | **0 帧** |
| 平均帧大小 | —（无帧） |
| 下行速率 | 0 B/s |
| 上行 | 0 B / 0 条 |

**读法**：**静默挂机 = 零广播**。25ms 的节流窗**不是心跳广播**（没有「每 25ms 发一份快照」这种事）——
只有 store 真的变了才推帧。唯一的定期流量是 **WS ping**（心跳 30s 一次，**控制帧**，不进应用载荷）。
⇒ **背景带宽不是问题**，也不存在「空闲时偷偷烧带宽」的病灶。

> 为什么有「静默期」：准备阶段会触发**异步的 agent 探测**（`detectedAgents` 逐个填进来），
> 准备刚结束时还有 2~3 帧在路上 —— 那属于**启动噪声**，不属于「挂机期广播」。静默期把余波排干净再开窗。

### 10.4 读法与结论（值不值得优化）

1. **带宽本身不是瓶颈** —— 压力口径（10Hz 交互）也只有 **46.5 KB/s**；折算到真人速率
   （~1 次交互/秒）**≈ 6.5 KB/s**。本地回环 WS 上这个量级毫无压力 ⇒
   **单看字节数，结论是「不值得为省带宽而动协议」**。
2. **但浪费是结构性的**：一次点击要重发 **6.4 KB 的整份状态**，而相邻两帧 **99.1% 的叶子字段一模一样**
   （一次点击通常只改了 `selection`）；真正变的部分只占全量帧的 **2.0%**。
   ⇒ 真正的成本不在网络，而在**客户端**（每帧反序列化 6.4 KB + 比对 + 可能重建）与
   **服务端**（每帧拼 6.4 KB JSON）。**这是本单最值得记的一条。**
3. **最大段 = `snapshot` 全量帧本身（98.5% 字节）**；帧内最大两块 =
   `characters`（26.6%）+ `units`（24.9%）= **51.5%**；
   其中 `detectedAgents`（21.6%）+ `projectInstances`（8.6%）= **30.2% 几乎是不变的常量**，
   每次交互都原样重发 —— **纯冗余**。
4. **位置事件已经走对了路**：`unit.position` 走 `event.push` **增量**（112 B/帧），
   而单位**业务表**走全量快照（1,584 B/帧）—— 同一件事的两面。
   ⇒ 「units 全量 / 增量」的分界线是**契约铁律**（`UnitView` 不含坐标，位置真相在世界层），
   不是随手挑的实现 ⇒ 想省这块只能动契约或动广播策略，不能在传输层绕过。
5. **帧数不是问题**：25ms 节流上限 = 40 帧/s，实测只有 **14 帧/s**（多数操作只改一两个字段，
   且连发操作被 25ms 窗合并）⇒ 节流已经把「帧数」压住了 ⇒ **优化方向是「让帧变小」，不是「让帧变少」**。
   （把窗口调回 50 / 100ms 能再省一半字节，但会直接吃掉 PERF-02 刚拿到的时延收益 ⇒ 不划算。）

### 10.5 候选排序（只登记，**本单不实现**）

| # | 候选 | 定位 | 证据 | 预期收益 | 风险 | 改动面 |
|---|---|---|---|---|---|---|
| ① | **delta 快照**（协议里已预留 `delta` 字段位） | `world-sync/protocol.ts` 的 `delta`（本期恒 `null`）+ `endpoint.ts` 的广播组装 | 相邻帧叶子相同率 **99.1%**；只发改动字段仅占全量帧 **2.0%** | 帧字节 **-90% 量级**（6.4 KB → 约 130 B） | **中高**：客户端从「全量覆盖」改成「合并」；重连仍需全量（协议 §1.2 的「全量即真相」要改写）；丢包/乱序要靠 seq 对账 | **契约层**（协议 + 客户端合并器；core 侧不动） |
| ② | **静态字段分层下发**（`detectedAgents` / `projectInstances` 变化时才推） | gateway 侧快照组装（`endpoint.ts` + `protocol.ts` 的 wire 形态） | 这两块占帧内 **30.2%**，几乎不变 | 帧字节 **-30%** | 中：客户端要合并两块「慢变字段」；字段归属要重新划线 | 小~中（gateway 侧为主，协议加两个可选字段位） |

③ 收益随时间增长；④ 收益可观但改动面最大 ⇒ **建议顺序 ② → ① → ③ → ④**
（先做小的、顺带把客户端的合并器验证出来，再上 ①）。

**但**：按 §10.4 第 1 条，**字节本身不是当前瓶颈** ⇒ 这四个候选**都不该急着做**；
真要动，触发条件应该是「客户端反序列化 / 重建成本被实测为问题」，而不是「字节数好看」。

> **顺序不变**，但三条注记必须一起读：② 的收益是**固定绝对值 1.9 KB/帧**（占比随规模 30% → 12%）；

| # | 缺口 | 影响 | 下一链怎么办 |

⇒ **delta 化（候选 ①）在长跑场景的收益远小于交互场景**（见 §11.5）。

### 11.3 场景 D · 大战场（28 单位）

**总量（与场景 B 同法、同长，只变规模）**

| 指标 | 场景 B（8 单位） | 场景 D（28 单位） | 比 |

| 下行总字节（60s） | 2,851,092 B | **7,028,890 B** | 2.47x |
| 下行帧数 | 840 | 839 | ≈ |

| 下行速率 | 46.40 KB/s | **114.40 KB/s** | 2.47x |

| `snapshot` 均帧 | 6,471 B | **16,210 B** | 2.50x |
| 上行 | 95,799 B / 639 条 | 94,894 B / 641 条 | ≈ |

**snapshot 帧内占比对比（B vs D）**

| 字段 | B 均帧字节（8 单位） | B 占比 | D 均帧字节（28 单位） | D 占比 | 占比漂移 |
|---|---|---|---|---|---|
| `characters` | 1,697 | 26.6% | **7,160** | **44.4%** | **+17.8pp** |
| `units` | 1,590 | 24.9% | **5,873** | **36.4%** | **+11.5pp** |
| **`characters` + `units` 合计** | **3,287** | **50.8%** | **13,033** | **80.4%** | **+29.6pp** |
| `detectedAgents` | 1,372 | 21.5% | 1,372 | 8.5% | **-13.0pp** |
| `projectInstances` | 545 | 8.5% | 545 | 3.4% | -5.1pp |
| **`detectedAgents` + `projectInstances`（慢变常量）合计** | **1,917** | **29.6%** | **1,917** | **11.8%** | **-17.8pp** |
| `missions` | 740 | 11.6% | 735 | 4.6% | -7.0pp |
| `notices` | 197 | 3.1% | 197 | 1.2% | -1.9pp |
| `selection` | 107 | 1.7% | 105 | 0.6% | -1.1pp |
| 其余（`activeInstanceId` / `directorEnabled` / `selectionGroups` / `layerHolds` / `messages` / `sessions` / `links` / `tasks` / `infoLayer`） | 76 | 1.2% | 74 | 0.5% | -0.7pp |
| （信封：`type` / `seq` / `delta`） | 97 | 1.5% | 97 | 0.6% | — |

**读法（这就是缺口 2 的结案）**

1. **§10.6 缺口 2 的假设成立、且比预想更强**：「`units` + `characters` ≈ 一半」**只在 8 单位时成立**；
   战场规模上去后它涨到 **80.4%** ⇒ **交互态的帧内结构随规模显著漂移**，
   ⇒ **任何按 8 单位测出来的占比都不能外推**（这正是本单要补这条缺口的原因）。
2. **漂移的机制**：慢变常量（`detectedAgents` / `projectInstances` / `notices`）的**绝对值恒定**
   （两个场景都是 1,917 B/帧，分毫不差）⇒ 分母变大 ⇒ 占比被稀释；
   而 `characters` / `units` **随单位数线性涨** ⇒ 占比同时被推高。
3. **单位成本基本恒定**（没有超线性爆炸）：
   `units` 每单位 **199 B**（B）→ **210 B**（D）；`characters` 每角色 **212 B**（B）→ **256 B**（D）。
   ⇒ D 的每角色多出来的 ~44 B 来自**名册物化的角色比手建角色多带 `roleId` / `instanceId` 两个镜像字段
   + 更长的派生 id**（`<roleId>_<instanceId>`，见 `character-id-rewrite.ts` 的 `deriveCharacterId`）；
   按两组均值反解：**名册角色 ≈ 265 B/个、手建角色 ≈ 205 B/个**（反解口径见 §11.6 缺口 5）。
4. **候选 ② 的收益因此缩水**：那两块慢变常量的**绝对值不变**（1,917 B/帧），
   但占比从 **29.6% 掉到 11.8%** ⇒ 候选 ② 在大战场只是「省 1.9 KB 的小修」，不是大头。

### 11.4 §10.6 缺口 2 / 4 / 7 的结案

| 缺口 | §10 的说法 | 本单结论 | 证据 |
|---|---|---|---|
| **2** 战场只有 8 单位，比例结构待验证 | 猜「`units` + `characters` ≈ 一半，随单位数上升会更显著」 | **确认，且更强**：**50.8%**（8 单位）→ **80.4%**（28 单位） | §11.3 对比表 |
| **4** `missions` 随记账线性变大，未量到顶 | 估「每条 ≈ 48 B；上限 64 条 ⇒ 单条任务封顶 ≈ 3.3 KB」 | **估算准确**：实测 **48~49 B/条**、**64 条确认封顶**（超限丢最旧、封顶后不再增长）⇒ 单任务封顶 **3.1~3.4 KB/帧**；但**长跑的大头另有其人** —— 任务条数（**211 B/条 × 100 条 = 21 KB/帧**） | §11.2 两条曲线 |
| **7** 未量长跑（>5min）与多任务并行的载荷上限 | — | **量到**：360s 长跑；**封顶帧 30,701 B**（`missions` 占 79.4%）；帧率 2.7/s；`tasks` 字段**全程恒 8 B**（空数组 —— 诚实说明见 §11.6 缺口 1） | §11.2 |

### 11.5 §10 候选排序复核 + 候选 ③ 的预期收益修正值

**候选 ③（`missions.checkpoints` 出广播面）—— 预期收益修正值**

| 口径 | 帧大小 | 检查点部分 | 修正后收益 |
|---|---|---|---|
| 场景 B（60s 交互，均 ~20 条检查点） | 6,471 B | ~0.96 KB | **-14.8%** |
| 场景 C · 单任务记满 64 条检查点 | 9,080 B | ~3.1 KB | **-34.2%** |
| 场景 C · 100 任务 + 64 检查点（长跑封顶帧） | 30,701 B | ~3.1 KB | **-10.1%** |

- §10.5 写的是「帧字节 **-10~30%**（随记账时长增长）」⇒ **修正为「-10% ~ -34%，但封顶在 ~3.1 KB/帧
  （64 条 × 48 B），不再随记账时长增长」**。
- **关键修正**：候选 ③ 只解决**检查点**。长跑封顶帧里 `missions` 的 **68.8%（21.1 KB）是任务记录本身**
  ⇒ **③ 单独做，长跑载荷只削掉 10%**。
  ⇒ **建议把 ③ 拆成两条**：
  - **③-a 检查点出广播面**（≈3.1 KB/帧，-10% ~ -34%）；
  - **③-b 任务条数出广播面 / 分页 / 降 `MAX_MISSIONS`**（≈21 KB/帧，**-69%** —— 长跑的大头）。
    ⚠️ 本单的任务条数曲线是**退化负载**（1.25s 建一条任务）⇒ 100 条是**契约上限**不是典型值；
    但它证明了「这条维度没有第二个上限兜着」。

**候选 ①（delta 快照）—— 收益随场景变化**

| 场景 | 「只发改动字段」占全量帧 | delta 后的帧字节收益 |
|---|---|---|
| 场景 B（交互） | 2.0% | **-98%** |
| 场景 D（大规模交互） | 0.8% | **-99.2%** |
| 场景 C（长跑记账） | **60.1%** | **-39.9%** |

⇒ §10.5 写的「帧字节 **-90% 量级**」在**交互态**成立（叶子相同率 99.1% / 99.6% 佐证）；
**长跑记账态只有 -40%** —— 因为 `missions` 每帧都在变。
⇒ **① 与 ③ 互补、不是替代关系**：先把「一直在变的那块」挪出广播面（③-a / ③-b），
  ① 的收益才回到 -98%。

**候选 ②（慢变字段分层下发）**

- 绝对收益恒定 **1,917 B/帧**（`detectedAgents` 1,372 + `projectInstances` 545）；
- 占比 **29.6%（8 单位）→ 11.8%（28 单位）** ⇒ **战场越大，它越不是大头**；
- 定位不变：**改动面最小、几乎纯 gateway 侧**的「先做的小修」—— 但别把它当主要收益项立项。

**候选 ④（按订阅裁剪）**

- 目标块 `characters` + `units` = **50.8%（8 单位）→ 80.4%（28 单位）** ⇒ **收益随规模上升**；
- 改动面仍最大（订阅语义 + 两端）。

**候选排序复核结论**

| # | 候选 | §10.5 的预期 | 本单修正 | 排序是否变 |
|---|---|---|---|---|
| ① | delta 快照 | -90% 量级 | 交互态 **-98% ~ -99.2%**；**长跑记账态只有 -39.9%** | **不变（第 1）**，但收益不再「无条件」 |
| ② | 慢变字段分层下发 | -30% | **-1.9 KB/帧（绝对值恒定）**；占比 29.6% → 11.8% | 不变，仍是「先做的小修」，**但不是大头** |
| ③ | `missions` 瘦身 | -10~30%，随记账时长增长 | **拆成 ③-a（-10% ~ -34%，封顶 3.1 KB/帧）与 ③-b（-69%，21 KB/帧）** | **不变（第 3），但范围必须拆开** |
| ④ | 按订阅裁剪 | -50% 量级 | 目标块占比 **51% → 80%** ⇒ 收益更大，改动面仍最大 | 不变（第 4） |

⇒ **§10.5 的建议顺序「② → ① → ③ → ④」本单复核后维持不变**，但补三条注记：

1. **② 降级为「小修」**：绝对收益只有 1.9 KB/帧（且**不随规模变大**），别当主要收益项立项。
2. **③ 必须拆成 ③-a / ③-b**：只做 ③-a 解决不了长跑（只削 10%）；
   **③-b（任务条数）才是长跑的大头**（21 KB/帧）。
3. **① 与 ③ 互补**：长跑态下 ① 的收益从 -98% 掉到 -40%
   ⇒ 若目标是**长跑**，**③-b 应排在 ① 之前**（把「一直在变的那块」挪走，① 的收益才回到 -98%）；
   若目标是**交互态**，① 仍是第一刀。

**§10.4 的总判断本单复核后仍成立**：即使在长跑封顶帧（30.7 KB / 帧）与 28 单位战场（114.4 KB/s），
本地回环 WS 上**带宽依然不是瓶颈** ⇒ 四个候选**都不该急着做**；
真要动的触发条件仍是「客户端反序列化 / 重建成本被实测为问题」。
**但缺口 4 / 7 的封顶数据补齐后，多了一条硬事实**：`missions` 字段在长跑里能占到帧的 **79.4%**、
单帧能到 **30.7 KB** ⇒ **若客户端将来要做「每帧重建 mission 列表」，成本会先于带宽成为问题** ⇒
候选 ③ 的**优先级由「收益不确定」上调为「收益有上限、但场景明确」**。

### 11.6 已知缺口 / 偏差（**读数前必读**）

| # | 缺口 / 偏差 | 影响 | 下一链怎么办 |
|---|---|---|---|
| 1 | 场景 C 的 `tasks` / `messages` / `sessions` **全程为空**（`tasks` 恒 8 B） | 「长跑里 tasks 会不会涨」**没量到** —— `task.assign` 会触发**真的派单链**（可能拉起外部 agent 进程），本单**刻意没碰** | 要量得单独立一单（受控 agent 桩），或改走 core 层直写 |
| 2 | 场景 C 的任务条数曲线是**退化负载**（1.25s 建一条任务） | 100 条是**契约上限**（`MAX_MISSIONS`），不是典型值；「21 KB/帧」是**上界**而非典型 | 真实工作台的多任务并行速率要另测；结论按「上界」读 |
| 3 | 场景 C 只测了「**一条**任务记到 64 条检查点」 | 「多条任务各记 64 条」的叠加上界（100 × 3.1 KB ≈ 300 KB/帧）**没量** | 若 ③-b 要动 `missions` 的广播面，这个叠加必须先量 |
| 4 | 场景 D 是 **28 单位**（roster 24 + 建档 4），没到 100+ 编制 | 占比漂移是**按线性外推**（每单位成本恒定），不是 100 单位实测 | 大编制另测（`MAX_CHARACTERS_PER_INSTANCE` = 64 ⇒ 单副本上限 64） |
| 5 | 场景 D 的「每角色 256 B」里，名册角色与手建角色的差异是**按两组均值反解**的 | 反解假设「两组各自同质」；单角色实际字节未逐字段核对 | 需要精确字段级拆分时另测 |
| 6 | 仍**单客户端** | 广播是「一份 payload × N 条连接」⇒ 多客户端时**服务端序列化成本 ×N**（§10.6 缺口 6 依旧） | 另测「N 客户端 × 帧率」的服务端 CPU |
| 7 | 仍**裸 WS 客户端** | 字节数偏小 < 0.5%；客户端 CPU / GC 成本**未量** | 客户端成本另立一单（浏览器侧） |
| 8 | 场景 C 的 `notices` 均帧 609 B（比 B 的 197 B 高） | 密集建单会累积提示（6s 过期），在**退化负载**下被放大 | 真实负载不会这么密集建单；按上界读 |

### 11.7 复跑方式

```bash
# 四个场景全跑（A/B/D 各 60s，C 360s；service 7800-7899 动态挑端口，临时 DATA_DIR，跑完按 pid 回收）
node e2e-tests/perf-broadcast.e2e.mjs --seconds 60 --long-seconds 360 --out /tmp/perf-broadcast-perf04.json

# 只补长跑（约 7 分钟）
node e2e-tests/perf-broadcast.e2e.mjs --only C --long-seconds 360

# 只补大战场（约 1 分钟）
node e2e-tests/perf-broadcast.e2e.mjs --only D --seconds 60
```

脚本改动（相对 PERF-03 版，**仍是零产品改动**）：

- 新增场景 C（长跑）与场景 D（大战场）；**场景配置集中在 `SCENARIOS` 表**（roster 数 / 目标单位数 / 负载模式）；
- 场景 D 的战场规模靠**脚本注入 roster**（副本根 `.stratix/roster` 写 N 个角色文件）⇒ 进场时按步 N6 物化；
- 新增 `--long-seconds`（场景 C 时长）与 `--only`（挑场景）两个开关；
  `--seconds` / `--out` / `--keep` 语义不变；
- 新增**逐帧载荷曲线采样**（`Meter.series`：帧字节 / `missions` 字段字节 / 检查点数 / 任务条数）
  ⇒ §11.2 的两条曲线是从**同一份原始 JSON**（`--out`）里算出来的，可复核；
- **回收纪律**：每个场景跑完按 pid 精确回收 service 进程并删临时目录（本轮实测残留 0 进程 / 0 临时目录）。
