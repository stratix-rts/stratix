§0结论先行

0.1现状三句话

  • 信息密度分配反了。顶栏塞了 19 个后代元素（8 个按钮 + 1 个音量滑条 + 3 个 on/off 文本 + 徽标 + 品牌 + 3 个计数），1280 宽下动作区独占视口宽 58.8%；而底栏因为写死 --hud-bottom-h: min(34cqh,300px)，在 1920×1080 下吃掉 300px（27.8% 视口高）。主播要操作的控件占了两头，观众要看的画面被挤到中间 65%。
  • 四角有真实碰撞，不是审美问题。按 src/hud/screens/main-screen.ts 的实际 CSS 值复刻并用无头浏览器实测：1280×720 下，跑马灯与命令面板重叠 26,250 px²、小地图与命令面板重叠 14,640 px²；回放时间戳角标与顶栏在任何分辨率下都重叠 5,160 px²（遮住品牌 "Stratix" 360 px²）。
  • 没有信息层级这个概念。6 类 HUD 信息（态势 / 操作 / 事件 / 演出 / 气泡 / toast）全部同时常亮、同一对比度。「▶ 60 秒看完今天」这种打断式演出进行时，HUD 一个都不让位；「🎬 导演」打开后，画面中央没有任何东西说明"镜头被接管了"。

0.2新版三句话

  • 中轴归地图。底栏从"34% 视口高 + 1100px 通栏"改成"内容自适应 + 控制岛（宽 56% 屏宽、约 92px）"，中轴可用高度从 59% 提到 80%+；左右两角（事件轨 ≤260px / 小地图 200×120）与控制岛零重叠。
  • 视线动线左下→中屏。事件条目从"纯展示文本"变成"可展开详情的入口"：hover 展开详情、点击锁定单位，中屏对应单位描边高亮，并画一条引导弧线把左下条目指向中屏单位——把 DEMO-PLAN §7「镜头自动订阅总线事件」从世界层的隐式行为，补成 HUD 层的显式连线。
  • 三层级 + 顶栏瘦身。常驻（L1）/ 事件（L2）/ 沉浸（L3）三档，L3 激活时 L1 自动降到 18% 对比；顶栏从 19 个元素降到 7 个（品牌 + 态势胶囊 + 徽标 + 🔊 / 🎬 / ▶ + ⋯），三个 on/off 文本标签删除，音量滑条收进 🔊 弹出层。

0.3承诺与边界

零删减承诺：现有 40 项 HUD 功能全部保留、全部可触达，只是换位置、换形态（常驻 → 收纳 / 折叠 / 弹出）。功能对照表逐项列出"现在在哪 → 新的在哪 → 变化类型"，无一项标记为"删除"。
本文件不改任何现有代码。所有 src/ 文件均为只读引用。涉及实施代价与需要改动源码的位置，集中写在 §5；其中 5 个需要拍板的取舍写在 §6。

1.2顶栏：一个 19 元素的横条

顶栏由 main-screen.ts:318-342 的 header.hud-topbar 渲染。它同时承担了三件互不相干的事：品牌（A1）、态势（A2）、操作（A4–A12）。

  • 它解决什么。主屏是"一切操作的入口"——没有更上层的菜单栏（§0 的交互三动词里，"点"这个动词的全部出口都在这条）。
  • 当初的取舍。DEMO-PLAN §8 明确"顶栏开关「演示」"、§7 明确"开关「🎬 导演」进 hud 顶栏"、§10 明确"总开关 + 音量 0-100"。也就是说，开关放顶栏是规格钦定的，不是随手放的。重构不能删开关，只能改形态。
  • 痛点。（a）19 个后代元素，1280 宽下动作区独占 58.8% 视口宽；（b）观众视角，8 个按钮里有 6 个是主播专属（换肤、聊天、会话、角色、设置、像素风），对观众零解释成本、纯噪声；（c）A13 三个 on/off 文本标签是 A4/A5/A6 状态的第二份表达——按钮点亮（variant=primary）已经表达了，再写一遍 "off" 是冗余；更糟的是它们没标 data-engineering，演示模式下依然显示（见 1.6）；（d）A8 音量滑条 84px 恒定占位，声音关掉时只是 disabled（main-screen.ts:381），仍在场。
取舍的合理内核要保留：顶栏是"唯一常驻的操作入口"，所以它必须一直可达。新版不拆散顶栏，只做收纳：把低频导航（聊天 / 会话 / 角色 / 设置 / 像素风）收进一个 ⋯ 溢出菜单，把音量滑条收进 🔊 的弹出层，保留 3 个开关一排直达。

1.3左下事件轨（跑马灯）

components/marquee/marquee.ts，position:fixed; left:16px; bottom:16px; z-index:21，定高 5 行（MARQUEE_METRICS.maxEntries = 5），每条 = 图标 + 短句 + 相对时间，左侧 3px 色条按分级取色（完成绿 / 报错红 / 派活蓝 / 里程碑金，色源 marqueeToneColor → 唯一事实源）。

  • 它解决什么。DEMO-PLAN §6："最近 5 条"。这是一条"窄带"——观众不需要日志抽屉，但需要知道"刚刚发生了什么"。它比 data-engineering 的日志抽屉更接近直播语言。
  • 当初的取舍。左下角是"第二眼区"——比正中央弱的注意力区，但比右上角的 toast 更持久（5 条常驻 vs toast 瞬时）。条数上限 5 是硬约束（MARQUEE_METRICS.maxEntries），也是性能约束（每条一个 DOM 节点 + 一个淡出计时器）。
  • 痛点。（a）与命令面板实撞：底栏通栏 1100px 在 1280 宽下左缘在 x=90，跑马灯右缘在 x≈265，重叠 26,250 px²；z-index 上跑马灯 21 < 底栏 25，所以是底栏压住跑马灯，两个半透明面板叠字。（b）条目是纯展示：push() 只渲染 icon / text / time，没有详情、没有"这条说的是哪个单位"，hover 也没有任何反馈（CSS 里 .entry 只有 transition 没有 hover 态）。（c）左下角同时是"高密度变动区"：跑马灯（5 条高频变动）+ 回放角标未来也在左附近 + 底栏贴底，三股东西在同一条底边抢。
可验证：marquee.ts:166-189 的 .entry 样式表中没有 :hover 规则；push()（223-247 行）只创建三个 span。条目上没有任何可交互语义。

1.4右下小地图

components/minimap/minimap.ts，fixed; right:12px; bottom:12px; z-index:45，画布 200×120（MINIMAP_METRICS，DEMO-PLAN §5 钦定"右下角 200×120px，岛屿轮廓 + 单位光点 + 当前视野白框"，装饰"外框描边 + 「MAP」角标"）。点击 = 镜头跳转（命中半径 8px，比点本身大一圈）。

  • 它解决什么。两个不同的问题塞在一个件里：给观众——"全景在哪、谁在哪"；给主播——"我要跳到哪儿"。
  • 当初的取舍。右下角 = 观众视线终点（看累了往右下收），且不与左下事件轨打架；200×120 是"能看出轮廓但不吃画面"的比例。
  • 痛点。（a）与命令面板实撞：小地图 x ∈ [1068,1268]，底栏命令面板 x ∈ [90,1190]，1280 宽下重叠 14,640 px²；且小地图 z-index 45 > 底栏 25，是小地图压住命令面板——最右一列命令按钮被盖。（b）右下角同时是"导航件"和"操作件"，两种用途挤在同一角。（c）200×120 是给主播的尺寸，观众其实只需要"有地图 + 一个白框"。

1.5底栏回放条

components/replay/day-replay.ts，挂在 main-screen.ts:350 的 .hud-replay-slot，位于底栏上沿、命令面板下方（底栏是 flex-direction: column，注释写明"挤进底栏而不是另开浮层：命令面板已经占了底部中央，回放条得贴着它才像同一条时间轴"）。内容：标题「今日回放」+ 时钟 + 条数 + 96 桶热力条 + 游标 + 「▶ 60 秒看完今天」。

  • 它解决什么。DEMO-PLAN §9："这是『一天 102 commit』故事的画面化，直播零风险保底素材"。回放条是保底叙事，不是实时信息。
  • 当初的取舍。热力条 = 单位密度；拖动 = 全天事件按时间重现（replay-controller.seek()：先发 reset 清场，再按序重放该时刻之前的 beat）；热力条只在数据指纹变化时重建（96 根柱子不逐帧重画）。
  • 痛点。（a）底栏容器高写死 min(34cqh,300px)——1920×1080 下 300px，1080 高的画面只剩 780px 给地图；1280×720 下 245px，剩 475px（66%）。（b）回放条与命令面板共用 1100px 通栏宽度，两个语义完全不同的控件（时间轴 vs 操作）被绑死在同一个宽度上，任何一方想变宽都会挤另一方。（c）回放时间戳角标（replay-clock.ts，fixed; top:24px; left:24px; z-index:40）与顶栏（z-index 30）重叠 5,160 px²，把品牌字遮掉 360 px²。

1.6单位气泡

src/world/objects/speech-bubble.ts，属于世界层（不是 HUD DOM）。规格 SPEECH_BUBBLE_SPEC：最大宽 160px、字号 13px、圆角 10px、最多 2 行、存活 4s、同屏 ≤3 个、同单位 5s 冷却；文案来自离线句库 world/speech-templates.ts（"这个我来！""搞定！""这有点不对…"）+ 20% 性格彩蛋。

  • 它解决什么。DEMO-PLAN §3：让单位"会说话"，给纯图形加人格。这是观众建立情感连接的唯一通道。
  • 当初的取舍。频率限制（同屏 ≤3、同单位 5s）是防刷屏的硬约束，不是可选优化。
  • 痛点。气泡在世界坐标里，HUD 事件在屏幕坐标里，两者没有任何连接。观众看到一条红色事件（"「小刚」卡住"）和世界里一个红色叹号单位，得自己认字认形把它们对上。这就是"视线动线断裂"的根源（详见 1.9 的 P9）。

1.7工程面板与演示模式

DEMO-PLAN §8 的设想是"演示的脸和干活的脸分离"：开启演示后隐藏全部工程件（raw json、task id 长串、时间戳列、日志 tab）、字号 +30%、信息密度下调。落地机制是 demo-mode.filterEngineering(host)：扫描 [data-engineering] 标记的节点并隐藏。

实测：全仓只有 1 个节点标了 data-engineering —— main-screen.ts:347 的日志抽屉。Agent 侧栏（E2）、态势总览（E3）、会话面板（E4）、以及顶栏的三个 on/off 文本标签（A13）都不在过滤范围内。也就是说 DEMO-PLAN §8 承诺的"工程面板隐藏"，当前落地率约 1/4。
  • 它解决什么。直播观众看到 "task id: 3f2a-…" 和四列时间戳日志，画面立刻从"哇它自己在干活"掉回"这是一个开发工具"。
  • 当初的取舍。用 data-engineering 属性做统一骨架，而不是每个面板各自判断——机制正确，覆盖不全。
  • 痛点。（a）过滤覆盖面不足（见上）；（b）过滤是整块隐藏，没有"降级"档——工程师想一边演示一边看日志做不到；（c）字体放大（DEMO_MODE.fontScale = 1.3）是全局 token 覆盖，会把顶栏那 19 个元素一起放大，放大的是最不需要被看的东西。

1.8其余常驻件

  • toast 宿主（F2）：fixed; top:0; right:0; z-index:50，右上角瞬时提示。位置合理（与顶栏同侧、瞬时、不占地图），是现有件里层级感最清楚的一个：它自己会消失。问题只有一个——它和顶栏右端的按钮区共享右上角空间。
  • 里程碑大字（B3）：fixed，屏幕中央，44–64px 金色大字 + 镜头震动 100ms。这是典型的 L3 沉浸演出，但目前没有任何 HUD 元素给它让位——大字压在地图正中央时，顶栏、跑马灯、小地图、回放条全部照常全亮。
  • 命令面板（E1）：12 条命令（6 条 selection scope + 6 条 global scope），grid-auto-flow: column、grid-auto-columns: minmax(6.5em, 1fr)，所以默认排成一行 12 列 ≈ 1100px。注意：面板按 scope 只显示其中 6 条（command-catalog.ts 里 selection 与 global 是两组），实际一行只有 6 个，1100px 是按 12 个算出来的预留宽度——这是一块富余的空白。

§2第二部分 · 新版布局论证

新版的每一条设计都挂在三条依据上。依据不成立，方案就不成立。

2.1依据一：直播画面构图（16:9 · 四角密度 · 中轴留白）

  • 16:9 的重心在中央偏下。观众看直播时，视线落在画面中央 60% 宽 × 中央 70% 高的区域；四角是"环境区"，用来放"不需要被找到"的东西。任何常驻在中央的高频变动元素，都会和叙事主体抢注意力。
  • 直播软件会叠东西。OBS / 直播伴侣常在画面上叠加评论流、摄像头小窗、字幕条。中央与底边中央是最容易被覆盖的位置。
  • 四角应该"低密度"。strong>现状把两个高频变动件放在底边两角（跑马灯 5 条 + 小地图光点），而底边中央又是控件区——底边整条都在动。
  • 结论。新版把底边中央的控制岛压扁（内容自适应，92px 而不是 245px），把高频变动的跑马灯从"5 条常驻"降为"2 条常驻 + 按需展开"，小地图保持右下但缩小存在感（观众态），底边整体静默度提升 3 倍以上。

2.2依据二：视线动线（重要事件：左下 → 中屏）

直播里"发生了一件事"和"这件事影响了谁"必须在同一次注视里被读到。现状的路径是：左下红字 → （自己找） → 中屏红叹号单位，跨屏且无引导。导演模式（§7）已经做了"镜头自己找事件"，但那是世界层的隐式行为，HUD 侧没有对应表达。

§5实施代价与风险

本节只做估算与定位，不改动任何源码。按改动面分三档。

档位涉及改动落点文件说明 / 风险
① 纯样式底栏高度改内容自适应、底栏宽度 1100→56%、事件轨宽度与 hover 样式、角标 inset、顶栏布局hud/screens/main-screen.ts 的 MAIN_SCREEN_STYLE；marquee.ts / day-replay.ts / replay-clock.ts 的 shadow CSS不碰 core 契约、不碰总线。风险：底栏高度自适应会改变左右侧栏的锚点（--hud-bottom-h 同时被 .hud-rail-left/right 的 bottom 引用），需一并改成 auto + 固定安全边
② 组件内部 DOM顶栏收纳（⋯ 菜单 + 🔊 弹出层）、事件详情展开、命令面板栅格列数、演示过滤覆盖面main-screen.ts 顶栏模板；marquee.ts push()；command-panel.ts 栅格；demo-mode.ts 的 data-engineering 标记最大的一块。风险：顶栏结构变化会波及 strat-button-click 事件委托（main-screen.ts:446-456）；命令面板栅格变化会波及 e2e 断言（e2e-tests/demo-flow.e2e.mjs 的 44 条演示断言需回归）
③ 需新增状态信息层级（L1/L2/L3）判定HUD 本地态，优先从 core 已广播的状态派生：WorldState.directorEnabled + 回放 playing + 里程碑触发不需要新增 core/types.ts 契约（除非要求"层级"能被外部观测）。这是本方案刻意守住的一条——core 契约只加不改是 DEMO-PLAN §12 的硬要求

性能约束（对齐 docs/PERFORMANCE_GUIDELINES.md）

  • 事件详情展开：按需创建，不预建 5 份隐藏 DOM；折叠时节点移除（与跑马灯现有的"淡出后移除"口径一致）。
  • 层级降对比：只改一个 CSS 自定义属性 / opacity，不触发逐帧重排。
  • 引导弧线：一条绝对定位的 div，用 transform 定位（不触发布局）；只在 hover / 点击态存在，不引入 rAF 循环。
  • 控制岛收窄后，回放热力条仍是 96 根柱子，且沿用现有"指纹不变不重建"策略（day-replay.ts:262-287）。
  • 所有新增计时器（若实现"展开 N 条"的展开动画计时）必须在 disconnectedCallback 清光——照抄 marquee.ts:211-221 的现有纪律。
最大的落地风险不是布局，是 e2e。e2e-tests/demo-flow.e2e.mjs 的 A/B/C 三段 44 条断言大量依赖顶栏按钮文本（如"演示""🎬 导演"）与命令面板按钮位置。顶栏收纳一旦落地，这些断言需要同步改写。这是本方案最贵的一处代价，必须在动手前先确认取舍（见 §6 Q1）。
