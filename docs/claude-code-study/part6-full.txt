2689: 27.2 这个文件最成熟的点， 是它不把所有失败都当成同一种失败
2690: 这里有几段判断特别能说明问题。
2691: 第—，  FOREGROUND_529_RETRY_SOURCES 明确区分了：
2692: 用戶正在等结果的前台请求
2693: 用戶根本感知不到的后台请求
2694: 只有前者才值得在容量雪崩时继续重试。
2695: 后者要尽快失败， 避免放大网关压力。
2696: 第二，  isPersistentRetryEnabled() 又引入了“无人值守会话” 的第三种世界：
2697: 普通前台会话

2701: .  人在等， 就可以多扛—下
2702: 人看不见， 就尽量别放大故障
2703: 人不在， 但任务必须跑完， 就进入持久重试
2704: 这是很强的系统设计意识。
2705: 27.3 fast mode、fallback、认证恢复被收进同一条故障链， 非常像线上系统
2706: 这个文件最“线上” 的地方， 是它没有把错误处理拆成很多互相不知道彼此存在的小 util， 而是把真实故障链条收在了—起。
2707: 比如：
2708: ·  fast mode 遇到短  retry-after， 直接短等后保留 cache 继续
2709: ·  fast mode 遇到长等待， 进入 cooldown， 切回标准速度， 避免 cache thrashing .  连续  529 达阈值时， 可能触发  fallbackModel
2710: ·  遇到  ECONNRESET /  EPIPE 这种 stale connection， 会禁用  keep-alive
2711: ·  Bedrock / Vertex 的认证错误， 会清掉各自云凭证缓存·   401 / OAuth revoked 会强制刷新令牌
2712: 这意味着 src/services/api/withRetry.ts 处理的其实不是“重试次数”， 而是：
2713: 一次模型调用在复杂线上环境里可能经历的故障路径图。
2714: 所以它会显得很重， 但这正是因为它吸收了真实世界的复杂度。
2715: 27.4 它用  AsyncGenerator   往外吐系统消息， 这一点非常漂亮
2716: with Retry() 最值得夸的设计之—， 是它不是简单返回—个  Promise&lt;T&gt;， 而是：
2717: AsyncGenerator&lt;SystemAPIErrorMessage, T&gt;
2718: 这意味着在等待重试期间， 它可以持续向外产出：
2719: .   api_retry
2720: ·  keep-alive 风格的 retry 提⽰
2721: 于是上层 runtime 不会只知道“还没返回”， 而是能把这段等待重新编进 Claude Code 的消息流。
2722: 这件事非常关键， 因为 Claude Code 是产品， 不是库。
2723: 当—次请求卡在重试期时， 宿主需要的是：
2724: .  可观测 .  可呈现 .  可中断
2725: 而不是“ 内部默默 sleep 30 秒”。
2726: 所以这个模块跟 src/services/api/claude.ts 的关系也很清楚： .   claude.ts 负责请求主循环
2727: .   with Retry.ts 负责失败路径的正式治理

2729: 这里还做了两个很重要的错误对象：
2730: CannotRetryError
2731: .   FallbackTriggered Error

2734: .  当前 retry context 是什么
2735: 这种结构化失败语义， 会让上层：
