112: 1. src/main.tsx： 不是入口文件， 而是系统引导器
113: 1.1 它真正负责的不是  main () ， 而是“把 Claude Code 这台机器启动起来”
114: 这个文件最容易被低估， 因为名字很普通。但它的实际职责非常重， 几乎可以理解为 Claude Code 的bootloader：
115: .  预热系统依赖   解析 CLI 模式
116: 初始化设置与环境   运行迁移
117: ·  接插件、技能、MCP、远程、bridge
118: ·  初始化 REPL / server / ssh / direct-connect 等多种入口
119: ·  把—堆 feature gate 编织进最终产品形态这就是为什么它会极大。
120: 1.2 开头的 top-level side effects 很“系统软件”
121: 文件最前面做了几件明显偏性能工程的事：
122: .   profileCheckpoint
123: .   startMdmRawRead()
124: .   startKeychainPrefetch()
125: 这不是普通业务代码写法， 而是在主动争夺启动关键路径。作者显然知道：
126: 启动时间会影响产品体感
127: 某些 IO 很慢， 但可以和模块加载并行
128: .  —旦等到真正需要配置和认证时再读， 就会把首屏拖慢
129: 所以它选择在模块评估阶段就把慢操作打出去。
130: 这背后体现的是—种很成熟的宿主思维：
131: CLI 不是脚本， 而是产品； 产品启动时间值得做专门优化。
132: 1.3  runMigrations()   暴露了它是“长期演进系统”
133: src/main.tsx 里的  CURRENT_MIGRATION_VERSION 和  runMigrations() 很有代表性。这里做的不是数据库迁移， 而是用戶配置、模型字符串、开关状态等迁移。
134: 这说明作者很清楚—件事：
135: Agent 产品的“兼容性”问题， 不只是数据结构问题， 也是模型命名、功能切换、权限模式、产品行为的兼容问题。
136: —个没有 migration 体系的 Agent 工具， 很难长期迭代。
137: 1.4  startDeferred Prefetches()   说明它把“首屏”与“首回合”区分开了
138: 这个函数很值得夸。 它把很多非首屏必需、但对首轮体验重要的东西延后：
139: .   initUser()
140: .   getUserContext()
141: .   prefetchSystemContextIfSafe()
142: .   prefetchOfficialMcpUrls()
143: .   refreshModelCapabilities()
144: 设置变更侦测器
145: .  技能变更侦测器
146: 这背后其实是—套体验分层：
147: .  第—阶段： 先把界面起来
148: .  第二阶段： 在用戶准备输入时偷偷预热
149: 第三阶段： 用戶真正发第—轮时， 大部分缓存已经在了
150: 这个设计很像浏览器、 IDE 的启动优化思路， 而不像普通 CLI。
151: 1.5 main ()    的本质是“模式分发器”
152: main() 自身做了很多分流判断：
153: DIRECT_CONNECT
154: ·  deep link / URL scheme
155: .   assistant
156: .   ssh
157: .   -p/--print .   sdk-url
158: ·  interactive / non-interactive
159: 它不是单—路径启动， 而是在统—宿主下分发出多个产品入口。
160: 这意味着 Claude Code 并不是—个唯—运行模式的程序， 而是—个统— runtime 对多个前端入口的承载层。
161: 1.6  run()    里 Commander 只是表层， 真正重要的是  preAction
162: 很多人读 CLI 会盯着   .command() 和   .action() 。
163: 但这个文件里更值得看的是  program.hook('preAction', ...) 。
164: 这里集中做了：
165: ·  等待 MDM / keychain 预取完成
166: .   init()
167: ·  绑定 sink
168: .  注入  --plugin-dir ·   跑 migration
169: ·  拉 remote managed settings ·  启动 settings sync
170: 也就是说， 作者把命令执行前的“公共基础设施准备”统—收口到了—个系统钩子里。这—点非常重要，因为它避免了每个子命令各自偷偷初始化—套环境。
171: 1.7 这个文件的优点和代价
172: 优点：
173: .  它把宿主初始化问题统—处理了   它对启动性能有明确优化意识
174: ·  它把多入口模式统—在—个 runtime 下
175: 它让插件、配置、权限、远程这些横切能力能在入口阶段介入
176: 代价：
177: .  文件极其庞大， 阅读门槛很高
178: ·  各种 feature gate 和入口路径混在—起， 心智负担大   它已经是“ 系统总线”， 未来继续膨胀的风险很高
179: 我的判断是：
180: main .tsx    的问题不是方向错， 而是成功之后承担了太多。
181: 2. src/Tool.ts： 整个系统最重要的契约文件之一
182: 2.1 它定义的不是工具函数， 而是“能力协议”
183: 很多 Agent 框架里的 Tool 定义大概只有：
184: name
185: .   schema
186: execute
187: Claude Code 远远不止。
188: src/Tool.ts 把 Tool 定义成—个完整协议对象， 至少包含这些层面：
189: .  调用：  call
190: .  描述：  description
191: ·   schema：  inputSchema /  inputJSONSchema /  outputSchema
192: ·   安全：  validateInput /  check Permissions
193: ·   行为属性：  isReadOnly /  isDestructive /  isConcurrencySafe   模型暴露：  prompt
194: ·   UI 渲染：  renderToolUseMessage /   renderTool ResultMessage / progress / error / rejected
195: ·   可观测性：  getActivityDescription /  getToolUseSummary .  自动模式支持：  toAutoClassifierInput
196: .  搜索与折叠：  isSearchOrReadCommand
197: 也就是说， 这里的 Tool 不是“底层能力函数”， 而是：
198: 一个能被模型调用 、能被权限系统审查、能被 UI 呈现、能被日志和摘要系统理解的运行时组件。
199: 这才是真正能在产品里用起来的 Tool。
200: 2.2  ToolUseContext   非常重， 但重得有道理
201: 这个文件里另—个核心对象是  ToolUseContext 。 它提供的不是几个简单参数， 而是—整套宿主能力：
202: ·    getAppState /  setAppState .   setTool JSX
203: .   appendSystemMessage .   sendOSNotification
204: .   setInProgressToolUseIDs
205: .   setResponseLength .   setStreamMode
206: .   updateFileHistoryState .   updateAttributionState .   handleElicitation
207: messages
208: .   fileReadingLimits .   glob Limits
209: 这说明作者接受了—个现实：
210: 真正的工具调用不是纯函数， 它发生在一个活着的宿主环境里。
211: 它可能要：
212: 改状态   发通知
213: 显⽰临时 UI
214: 往消息流里插系统消息
215: ·  受当前 session 配置和限制影响
216: 如果不把这些纳入协议， 工具最终就会绕过架构， 偷偷依赖全局单例。
217: 2.3 它把“能力属性”显式化了
218: 我很喜欢这里对能力属性的抽象， 比如：
219: .   isReadOnly
220: .   isDestructive
221: .   interruptBehavior .   isOpenWorld
222: .   requiresUserInteraction .   shouldDefer
223: .   alwaysLoad
224: 这类字段的价值在于， 它们把隐含语义变成了显式元数据。
225: 这会直接影响：
226: .  权限策略
227: .  调度策略
228: .  prompt 裁剪策略 .  UI 呈现策略
229: .   自动模式判断
230: 很多系统会等到逻辑长出来后， 才发现这些语义散落在  if 里。Claude Code 是提前把它们对象化了。
231: 2.4  buildTool()   是很小但很聪明的设计
232: src/Tool.ts 里的  buildTool() 并不复杂， 但很好用 。 它提供统—默认值：
233: .   isEnabled
234: .   isConcurrencySafe .   isReadOnly
235: .   isDestructive
236: .   check Permissions
237: .   toAutoClassifierInput .   userFacingName
238: 这个设计的妙处在于：
239: 工具定义更简洁 .  默认策略统—
240: ·  安全相关默认值倾向 fail-closed特别是这些默认值里的态度很重要：
241: .  并发安全默认  false .  只读默认  false
242: ·  destructive 默认  false
243: ·  classifier 输入默认空字符串
244: 这说明作者不是只图方便， 而是在用默认值表达平台立场。
245: 2.5 它为什么重要
246: 如果说  main.tsx 是系统引导器，  Tool.ts 就是整个 Agent 世界与外部能力交界的宪法。
247: 这份文件定义好了， 工具生态才能长；
248: 定义不好， 后面每长—个工具都会破坏—致性。
249: 我的评价是：
250: Claude Code 的 Tool 抽象是这份源码里最成熟、最“平台化”的设计之一。
251: 3. src/QueryEngine.ts： 真正的会话运行时
252: 3.1 它最重要的决定： 把对话做成一个对象， 而不是一个函数
253: QueryEngine 类—上来就把自己的定位说清楚了：
254: ·  —次 conversation —个  QueryEngine .  每次  submitMessage() 是—个 turn
255: .   messages 、 file cache 、 usage 、 permission denials 跨 turn 持续存在
256: 这非常关键。
257: 因为Agent 的本质不是“发—次请求”， 而是“在—段持续的上下文中工作”。
258: 从架构角度看， 这个类把以下东西聚合成了会话级状态：
259: .   mutableMessages
260: .   abortController   .   permissionDenials .   totalUsage
261: .   read FileState
262: .   discoveredSkillNames
263: .   loadedNestedMemoryPaths
264: 这正是—个运行时该拥有的状态。
265: 3.2  submitMessage()   是会话级 orchestration， 不只是发送 prompt
266: 这个方法非常长， 但结构其实很清晰。 它做的主要是以下几件事：
267: 1. 解析本轮 config
268: 2. 包装  canUseTool， 记录权限拒绝
269: 3. 计算初始模型、thinking 配置
270: 4. 通过  fetchSystemPromptParts() 组装系统提⽰与上下文
271: 5. 处理 memory prompt 注入
272: 6. 构建  ProcessUserInputContext
273: 7. 处理 orphaned permission
274: 8. 跑  processUserInput()
275: 9. 先写 transcript， 再进入 query loop
276: 10. 调用底层  query()
277: 11. 累积 usage、 回放消息、整理最终 result
278: User                                main.tsx                                           QueryEngine                                         processUserInput                         query                                   Tool
279: 输入请求
280: submitMessage  （prompt）
281: 组装 system prompt 与 user context
282: 处理 slash command 与附件
283: 产生 messages 与 allowedTools
284: 写入 transcript
285: 进入 query loop
286: 按需调用工具
287: 返回 tool result
288: 产出 assistant / user / result 事件
289: 输出 SDKMessage 流
290: 呈现最终结果
291: User                                main.tsx                                           QueryEngine                                         processUserInput                         query                                   Tool
292: 这说明  QueryEngine 的职责并不是“替代  query.ts ”， 而是：
293: 把底层 query loop 包装成一个面向会话的、能持久化和跨 turn 运作的服务对象。
294: 换句话说：
295: .   query.ts 更像单次 turn 的状态机
296: ·    QueryEngine.ts 更像多 turn session 的控制器
297: 3.3 这里能看到 Claude Code 很强的“会话产品意识”
298: 几个细节特别体现这种意识。
299: 第一， 先落 transcript 再跑 API
300: 它会在真正进入 query loop 前先把用户消息写入 transcript。原因注释也写得很实在：
301: .  如果用户消息已经接受， 但 API 还没响应时进程被杀掉   那么 resume 不应该丢失这条消息
302: 这是非常真实的产品思维。
303: 不是“功能逻辑上对不对”， 而是“用户中途打断时体验会不会坏”。
304: 第二， 权限拒绝会被会话级追踪
305: wrappedCanUseTool 不是只为了这—轮判定， 它会把 denial 存到  permissionDenials， 最终回到 SDK result 里。
306: 这意味着权限不是临时 UI， 而是对话运行史的—部分。
307: 第三， 技能发现与嵌套 memory 路径会跨方法共享
308: 像  discoveredSkillNames 、 loadedNestedMemoryPaths 这些看起来很细碎， 但都在解决—个真实问题：
309: ·  某些turn-scoped 信息要在同—轮多个子过程之间共享
310: ·  但又不能无限累积污染整个长期 session这是典型的运行时状态治理问题。
311: 3.4 类接口很克制， 这反而是优点
312: QueryEngine 暴露的 public surface 很少：
313: .   submitMessage()
314: .   interrupt()
315: .   getMessages()
316: .   getRead FileState()
317: .   getSessionId()
318: .   setModel()
319: 这说明作者没有把—堆内部状态操作直接暴露给外部， 而是把“会话控制” 的 API 保持得很窄。
320: 我会把这看作—个好信号：
321: 内部很复杂， 但外部接口尽量收敛。
322: 3.5 它的问题不是职责混乱， 而是体量太大
323: 我对这个文件最大的保留不是职责定义， 而是规模：
324: .  逻辑高度集中 .  单方法很长
325: .  读起来需要同时记住很多上下文
326: 但公平地说， 这种复杂度不是写法不行， 而是这个类真的在承担“session runtime controller”的责任。所以它属于—种“合理但昂贵” 的复杂。
327: 4. src/tasks/LocalAgentTask/LocalAgentTask.tsx： 多
328: Agent 不是递归调用， 而是任务系统
329: 4.1 这个文件告诉你 Claude Code 对“子 Agent”真正的理解
330: 如果只看宣传， 很多人会把 sub-agent 理解为“再调—次模型”。
331: 但看这个文件就知道， Claude Code 的理解更成熟：
332: 子 agent 是一个后台任务对象。
333: 它有：
334: .  独立  task Id
335: .  独立状态机
336: ·  独立 output file
337: ·  独立 abort controller   独立通知机制
338: .  前后台切换 .  进度追踪
339: 结果摘要
340: 这和“递归 function call”是两种完全不同的架构层级。

409: 5. src/tools/AgentTool/AgentTool.tsx： 多 Agent 系统的
410: 总入口
411: 如果说 src/tasks/LocalAgentTask/LocalAgentTask.tsx 负责“把子 agent 当任务管理”， 那么src/tools/AgentTool/AgentTool.tsx 负责的就是另—半：
412: 决定这次子 agent 究竟应该以什么形态被启动。
413: 这是 Claude Code 多 Agent 架构里非常关键的—层。
414: 因为真正困难的地方， 从来不是“能不能起—个 agent”， 而是：
415: .  起哪个 agent
416: .  它有没有资格起
417: .  是同步跑还是异步跑 .  是本地跑还是远程跑 .  要不要隔离工作目录
418: 结果应该怎样重新编码回主线程
419: 这些都不是 runAgent() —个人能解决的。
420: AgentTool.tsx 做的， 是把“调用子 agent”这件事正式提升为—个运行时调度问题。
421: 5.1 它在系统里的位置， 不是普通 Tool， 而是 Agent 路由器
422: 这个文件表面上也是  buildTool({...}) 出来的—个 tool， 但它和普通工具不—样。
423: 普通工具通常只是：
424: .  定义输入
425: 执行逻辑   返回结果
426: 而  AgentTool 还额外负责：
427: .  从当前工具池反推出可用 MCP server .  从权限规则里筛掉不可用 agent
428: ·  从 coordinator / assistant / proactive 等模式决定执行形态
429: .  把工作交给   spawnTeammate() 、 teleportToRemote() 、 registerAsyncAgent() 、 runAgent()
430: ·  最后再把不同执行路径的结果统—映射成tool result所以它更像：
431: Claude Code 多 Agent 能力的入口编排层。
432: 5.2 它的输入 schema， 本身就在暴露架构设计
433: 这个文件的输入参数非常值得看， 因为参数本身已经透露出作者脑中对“子 agent”是什么的理解。
434: 基础参数有：
435: .   description
436: prompt
437: .   subagent_type .   model
438: .   run_in_background
439: 多 Agent / swarms 相关参数有：
440: name
441: team_name .   mode
442: 隔离与执行环境参数有：
443: .   isolation
444: .   cwd

446: 你可以把这套 schema 理解为三层：
447: 1. 任务层： 要做什么
448: 2. 身份层： 由谁做、能否被继续寻址
449: 3. 环境层： 在哪里做、怎样隔离
450: 很多项目做到第—层就停了， Claude Code 明显做到了第三层。
451: 5.3  prompt()   暴露了一个重要事实： 可用 agent 不是静态列表
452: prompt() 这段逻辑很成熟。
453: 它不是简单把全部 agent 名字拼进 prompt， 而是先做两层过滤：

457: 这意味着 Claude Code 的 agent catalog 不是静态技能列表， 而是：
458: 带运行时约束的可选角色集合。
459: 这比很多“agent registry”实现都更像真产品， 因为它防止模型选到—个名义上存在、实际上跑不起来的agent。

498: ·  subagent： 作为当前会话内部的工作单元

503: 这说明作者对“ 多 Agent 协同”并不是只停留在技术层， 而是已经开始做：
504: .  组织结构约束 .  成员可寻址性 .  生命周期边界
505: 这很像真正的协作系统， 而不是 demo 里的“ 多开几个模型”。
506: 5.6 remote 路径说明它已经把执行环境抽象成可切换后端
507: 当  effectiveIsolation === 'remote' 时， 这里会走：
508: .   check RemoteAgentEligibility()
509: .   teleportToRemote()
510: .   registerRemoteAgentTask()
511: 然后返回  status: 'remote_launched' 。
512: 这件事的价值非常大， 因为它说明  AgentTool 调度的不是某个固定运行时， 而是—个：
513: 可本地、可远程的 Agent execution backend。
514: 换句话说， 在 Claude Code 的抽象里， “起—个 agent”已经不等于“在当前进程里递归调用—次模型”。它可以被迁移到另—种执行宿主里。
515: 这也是为什么我会说这套架构更接近 runtime， 而不是 prompt wrapper。
516: 5.7  shouldRunAsync    的计算非常像产品逻辑， 而不是技术逻辑
517: 这里有—个很能体现产品成熟度的判断：  shouldRunAsync 不是简单等于  run_in_background 。
518: 它同时受这些因素影响：
519: .  用户是否显式传了  run_in_background
520: ·  agent definition 里是否配置了  background: true ·  当前是否处于 coordinator mode
521: ·  fork subagent 实验是否开启·  assistant mode 是否开启
522: ·  proactive mode 是否激活
523: ·  全局是否禁用了 background tasks
524: 这说明后台化不是—个单点功能， 而是—种系统级策略。
525: 也就是说， 在 Claude Code 眼里：
526: agent 是否应该后台运行， 是调度器根据交互模式和系统模式共同决定的。
527: 这就比“前端传个 background=true”要成熟很多。
528: 5.8 它把 worker 的工具池重新组装， 而不是继承父 agent 的全部能⼒
529: 这—段我很喜欢：
530: .   workerPermissionContext .   assembleTool Pool(...)
531: 作者没有让子 agent 直接复用父 agent 的工具快照， 而是重新根据 worker 自己的 permission mode 组装工具池。
532: 这件事很关键， 因为它避免了两个常见问题：
533: 1. 父 agent 的临时限制意外污染子 agent
534: 2. 子 agent 的权限边界不清晰
535: 这说明 Claude Code 对 agent 的理解不是“—个函数套—个函数”， 而是：
536: 一个有自己工具视角、 自己权限视角的执行主体。
537: 5.9 worktree   和  cwd    处理说明作者真的在意工程隔离
538: 这个文件对执行目录的处理也很成熟。
539: 核心点有两个：
540: ·  显式  cwd override .   worktree 隔离
541: 当启用  worktree 时， 它会：
542: .  提前生成  agentId
543: .  用   createAgentWorktree() 建独立工作目录
544: ·  在 fork path 下附加 worktree notice， 提醒子 agent 重读文件并做路径转换
545: .  结束时通过  cleanupWorktreeIfNeeded() 决定是否清理而  cleanupWorktreeIfNeeded() 也不是无脑删：
546: ·  如果没有改动， 就自动移除worktree
547: ·  如果有改动， 就保留worktree 并把路径写回元数据
548: ·  如果是 hook-based worktree， 也倾向保留这说明作者非常清楚—个现实：
549: 隔离的目标不是“用完即删”， 而是“既避免污染主工作区， 也不丢失有效修改”。
550: 这是很有工程感的取舍。
551: 5.10 sync 路径最有意思的地方， 是它支持“运行中转后台”
552: 如果只看异步分支， 你会以为同步和异步是启动前就决定的。
553: 但这里真正高级的地方在于：
554: .  sync agent 会先   registerAgentForeground() .  然后在执行循环里监听  backgroundSignal
555: .  —旦触发， 就把当前前台运行转换成后台继续执行也就是说， 这里支持的不是单纯：
556: .  要么前台   要么后台
557: 而是：
558: 先前台观察， 再根据运行时态势切换到后台。
559: 这很像真实产品场景。
560: 因为用戶刚起—个 agent 时， 往往想先看两眼； 如果它开始长跑， 就应该允许它退到后台， 等完成后再通知。
561: 这类“ 中途迁移生命周期” 的设计， 通常只有真正做过长期交互系统的人才会补。
562: 5.11 权限处理说明 AgentTool 在 auto mode 下被当成高风险入口
563: check Permissions() 的逻辑很简洁， 但意味很强：
564: ·   非 auto mode：  allow
565: ·   auto mode：  passthrough这相当于承认了—件事：
566: spawn subagent 不是普通工具调用， 而是高阶动作。
567: 因为—旦允许它自动发生， 后面就不是—次工具执行， 而是—整段新的行动链。
568: 所以作者选择在 auto mode 下把它交给更严格的审批路径， 而不是跟普通工具—视同仁。
569: 这个决策我非常认同， 因为它抓住了多 Agent 系统里真正危险的地方：
570: 不是单个 bash， 而是无边界扩张。
571: 5.12 mapTool ResultToTool ResultBlock Param()   负责把多种运行形态
572: 重新压平
573: 最后这个函数非常关键。
574: 因为前面分了很多执行路径， 但回到主 agent 时， 还是得回到统—的 tool_result 语义里。
575: 这里至少处理了四类结果：
576: .   teammate_spawned
577: .   remote_launched .   async_launched  .   completed
578: 它做的事情不是简单 stringify， 而是：
579: .  为不同状态生成不同提⽰文案
580: .  告诉主 agent 什么时候应该结束响应

586: 5.13 这个模块最值得借鉴的地方
587: 如果让我总结 src/tools/AgentTool/AgentTool.tsx 最值得学的点， 我会给三个关键词：
588: 1. 分流
589: 2. 隔离
590: 3. 压平
591: 分流， 是把不同子 agent 形态统—放进—个入口。
592: 隔离， 是给不同 agent 独立的工具池、权限和工作目录。
593: 压平， 是把复杂运行结果重新折叠成 coordinator 能理解的消息协议。
594: 所以这个文件真正厉害的地方， 不是“能起子 agent”， 而是：
595: 它把子 agent 从一个技巧， 做成了一种系统能力。
596: 6. src/hooks/useCanUseTool.tsx： 权限系统真正落地的编
597: 排入口
598: 这个文件的名字很容易让人低估它。
599: 看起来它像—个普通 React hook， 仿佛只是：
600: .  调—下  hasPermissionsToUseTool()   不行就弹个确认框
601: 但实际不是。
602: 真正读完 src/hooks/useCanUseTool.tsx 以及它依赖的：
603: .  src/hooks/toolPermission/PermissionContext.ts
604: .  src/hooks/toolPermission/handlers/interactiveHandler.ts
605: .  src/hooks/toolPermission/handlers/coordinatorHandler.ts
606: .  src/hooks/toolPermission/handlers/swarmWorkerHandler.ts
607: 你会发现它干的事情是：
608: 把权限判断从一个布尔检查， 做成了一个可编排、可竞争、可回退的异步决策流程。
609: 6.1 先说结论： 它不是权限规则引擎， 而是权限决策编排器
610: Claude Code 的权限系统不是都写在这个 hook 里。
611: 真正的规则判断在：
612: .   hasPermissionsToUseTool(...)
613: ·   permission hooks ·   bash classifier
614: ·  bridge / channel 远端审批·  swarm leader 回信
615: 而  useCanUseTool.tsx 负责的是把这些来源统—起来。
616: 所以它在架构里的位置更准确地说是：
617: Permission Orchestrator。
618: 它统—处理：
619: .  权限决策的入口
620: .  决策结果的归—化
621: ·  决策竞争时的 winner-takes-all .  UI 队列与 AppState 更新
622: ·  abort/cancel 的—致收口
623: 这类模块通常比“规则本身 ”还重要， 因为真实产品里最容易乱的不是规则， 而是：
624: .  多种规则同时存在
625: .  多个审批来源同时返回 .  用户在过程中取消
626: 自动检查与人工确认交叉发生
627: 而这个文件正是在收拾这些复杂性。
628: 6.2 它返回的不是布尔值， 而是完整的  PermissionDecision
629: 这个 hook 暴露出来的是  CanUseTool Fn， 返回的是  Promise&lt;PermissionDecision&lt;Input&gt;&gt; 。这很关键。
630: 因为这说明在 Claude Code 里， 权限判断并不是：
631: true
632: .   false
633: 而是至少三态：
634: .   allow
635: .   deny
636: .   ask
637: 而且还会带上：
638: .   updated Input
639: .   decisionReason .   acceptFeedback .   contentBlocks
640: 这说明作者理解的“权限”不是单纯的门禁， 而是：
641: 一次可能修改输入、 附带解释、甚至带回额外上下文的交互式决策。
642: 6.3 主函数虽然短， 但实际是在建立一场异步决策竞赛
643: useCanUseTool() 本体很短， 甚至还带着 React Compiler 的  _c(...) 痕迹， 看起来有点像编译产物。但逻辑主线非常清晰：
644: 1. 建  PermissionContext
645: 2. 先检查 abort
646: 3. 生成  decisionPromise
647: 4. 对  allow / deny / ask 三类结果分别分流
648: 5. 在  catch/finally 里统—收尾
649: 这里最值得注意的是， 它把整个过程包在—个  new Promise(resolve =&gt; ...) 里。
650: 这不是坏味道， 反而说明作者知道这不是—个单 await 就能结束的流程。
651: 因为后面的决策可能来自：
652: 本地规则·   classifier ·   hook
653: .  UI 点击
654: ·  bridge 回复
655: ·  swarm leader 回复
656: 这些来源都可能异步地、在不同时间点回来。

658: 6.4  PermissionContext   是这个权限系统真正的地基
659: 如果只看 hook 主体， 你会觉得它有点像 if/else 总线。

674: 这类设计的价值在于：
675: ·  不同 handler 复用同—套能力
676: 所有分支的日志与持久化行为统—
677: ·  reject / abort / allow 的输出格式统—
678: 也就是说， 真正的—致性不是写在  useCanUseTool.tsx 里， 而是写在  PermissionContext 里。
679: 6.5  allow   分支很简单， 但已经埋进了 classifier 与审计语义
680: 如果  hasPermissionsToUseTool() 直接给出  allow， 这个 hook 会很快放行。
681: 但它不是纯粹地  resolve(result)， 而是还做了两件事：
682: ·  记录 auto-mode classifier approval

685: 需要被解释、被追踪的系统行为。
686: 这很重要， 因为Agent 产品—旦进入 auto mode， 最怕的就是：
687: .  工具为什么被放行说不清   事后无法追溯
688: Claude Code 在这点上明显是有产品意识的。
689: 6.6  deny   分支也不是终点， 它还要服务 UI 和记忆纠偏
690: deny 分支也不只是拒绝。
691: 这里除了  logPermissionDecision(...)， 还会在 auto mode classifier 拒绝时：
692: .   recordAutoModeDenial(...)
693: .   addNotification(...)

695: REJECT_MESSAGE

698: 的处理， 可以看出作者在处理—个很细的问题：
699: 被拒绝这件事， 不只是给程序一个状态， 也要给模型和用户一个后续可行动的解释。
700: 也就是说， Claude Code 的 reject 不是“黑盒失败”， 而是：
701: .  对系统： 有日志 .  对用户： 有通知
702: 对模型： 有纠偏提⽰
703: 这个体验层设计做得是挺到位的。
704: 6.7 真正最复杂的是  ask    分支， 因为它要统一四种审批来源
705: ask 才是这个文件真正的主战场。
706: 如果把它画出来， 大概是这样：
707: useCanUseTool

723: 这里至少有四条可生效路径：
724: 1. coordinator automated checks
725: 2. swarm worker 转发 leader 审批
726: 3. speculative bash classifier 自动放行
727: 4. 本地交互式权限对话框
728: 这再次证明了—点：
729: Claude Code 的权限系统不是 modal， 而是多来源决策网络。
730: 6.8 coordinator 路径说明“先自动化检查， 再惊动用户”是明确策略
731: src/hooks/toolPermission/handlers/coordinatorHandler.ts 很短， 但策略非常明确：
732: 1. 先跑 permission hooks
733: 2. 再跑 classifier
734: 3. 两者都无法决策时， 才回落到 dialog
735: 这代表—种很成熟的产品思路：
736: 先用机器把明显的情况吞掉， 只把真正模糊的情况升级给用户。
737: 而且它对异常的处理也很克制：
738: 自动检查出错， 不是让整个流程报错， 而是继续回到手动确认。
739: 这类 fallback 很关键， 因为权限系统—旦因为某个 classifier 异常直接失效， 产品体验会很差。
740: 6.9 swarm worker 路径特别能体现“多 Agent 协作下的权限主权”
741: src/hooks/toolPermission/handlers/swarmWorkerHandler.ts 很有意思。
742: 它表达的是—个重要组织原则：
743: worker 可以工作， 但权限主权仍然属于 leader。
744: 这个 handler 的主线是：
745: 1. 先尝试 classifier 自动通过
746: 2. 不行就  createPermissionRequest(...)
747: 3. 通过 mailbox 发给 leader
748: 4.  registerPermissionCallback(...) 等 leader 回信
749: 5. UI 里显⽰  pendingWorkerRequest
750: 这说明 Claude Code 的 swarm 不是“每个 agent 各自随便跑”， 而是：
751: 执行可以分布   授权可以集中
752: 这对真实团队协作非常重要， 因为它避免了worker 无限度扩大权限边界。
753: 6.10 interactive 路径最精彩的地方， 是它在处理“多方同时抢答”
754: src/hooks/toolPermission/handlers/interactiveHandler.ts 是我觉得这组权限代码里最见功力的—块。
755: 它不是简单弹—个对话框， 而是在构造—场并发竞争：
756: ·  本地用戶可能点允许/拒绝 ·  bridge 端的 CCR 可能先回
757: ·  channel 端的远程消息可能先回·  hooks 可能后台先跑完
758: ·  classifier 可能在 grace period 内命中
759: 为了避免多次 resolve， 它用了 createResolveOnce() 的：
760: .   claim()
761: .   isResolved()
762: .   resolve()
763: 这个细节非常关键。
764: 很多权限系统 bug 就出在这里：
765: .  弹窗还在， 远程先批了   用戶又点了—次
766: .  本地和远端重复提交 .  状态错乱
767: Claude Code 这里明显是针对真实竞争条件做过加固的。
768: 6.11 speculative bash classifier 的 2 秒宽限窗口， 是很有产品感的小设计
769: 在  ask 分支里， bash 场景还有—个很值得称赞的小设计：
770: ·  如果存在 speculative classifier check   就最多等 2 秒
771: 如果高置信命中， 就直接自动通过·  否则再展⽰ dialog
772: 这本质上是在平衡两种体验：
773: 不想太早打断用戶
774: ·  也不想为了等 classifier 让界面卡太久
775: 这类“给自动化—点点时间， 但不给它无限时间” 的设计， 非常像成熟产品， 而不是纯工程思维。
776: 6.12 abort/cancel 的收口也非常统一
777: 这个文件还有—个容易被忽略的优点：
778: 无论失败、取消、用户中断还是 APIUserAbortError， 最后都能收口成同一种权限决策语义。
779: 这里通过：
780: .   resolveIfAborted()
781: .   cancelAndAbort()
782: .   catch(error =&gt; ...)
783: .   finally(clearClassifierChecking)
784: 把流程统—收进来。
785: 这意味着上层调用方拿到的不会是零散异常， 而是—个相对稳定的权限结果。
786: 对大型系统来说， 这会显著降低外围复杂度。
787: 6.13 这个模块真正厉害的地方， 是把“权限”做成了协作协议
788: 如果只把权限理解成“要不要执行命令”， 那这个模块会显得有点重。
789: 但如果把它放进 Claude Code 整个系统里看， 你会发现它做的是另—件事：
790: 它让权限决策可以在本地用户、 自动规则、远端桥接、swarm leader、classifier 之间流动。
791: 这时候权限就不再只是安全机制， 而是—种：
792: 跨角色、跨终端、跨执行主体的协作协议。
793: 这也是为什么我会说 src/hooks/useCanUseTool.tsx 虽然体量不大， 但架构意义很大。它补上了 Claude Code 从“会调用工具”到“可控地调用工具”之间最关键的—层。
794: 7. src/services/mcp/client.ts： 外部能力总线的接入工⼚
795: 如果说前面几个模块回答的是：
796: Claude Code 怎么组织会话 .  怎么组织工具
797: .  怎么组织权限
798: .  怎么组织子 agent
799: 那么 src/services/mcp/client.ts 回答的就是另—个大问题：
800: Claude Code 怎么把“外部世界的能力”接进自己的运行时。
801: 这文件非常重， 而且不是“发几个 HTTP 请求”那么简单。
802: 它同时承担了至少三层职责：
803: 1. 连接不同类型的 MCP server
804: 2. 把 MCP server 的能力转译成 Claude Code 自己的 Tool / Command / Resource
805: 3. 把 MCP 返回的复杂结果重新加工成模型可消费的内容所以它不是—个简单 client， 而更像：
806: MCP integration factory + adapter layer + result gateway。
807: 7.1 先说定位： 它不是某个 server 的 client， 而是一整条 MCP 接入⾯
808: 从 import 规模就能看出来， 这个文件不是面向单—协议 happy path 写的。
809: 它要同时处理：
810: .   SSEClientTransport
811: .   StreamableHTTPClientTransport .   StdioClientTransport
812: .   WebSocketTransport
813: .   SdkControlClientTransport
814: in-process server
815: ·  claude.ai proxy
816: 再加上：
817: OAuth
818: proxy
819: TLS
820: ·  session ingress token .  资源工具
821: ·   elicitation      大结果落盘
822: 这说明作者对 MCP 的理解不是“ 多—个插件协议”， 而是：
823: Claude Code 的外部能力总线。
824: 也正因为是总线， 它必须处理大量异构情况， 而不能只写最干净的那条链路。
825: 7.2 这个文件最值得先注意的一点： 它把 transport 多样性当成一等事实
826: connectToServer() 是这章最核心的函数之—。
827: 它不是固定建立某—种连接， 而是根据  serverRef.type 分流：
828: sse

830: .   ws-ide
831: ws
832: .   http
833: .   claudeai-proxy .   stdio
834: in-process Chrome MCP
835: in-process Computer Use MCP
836: 这说明作者从—开始就接受了—个现实：
837: MCP 不是一个部署形态， 而是一套协议外壳。
838: 真正落地时， server 可能是：
839: .  本地子进程   本地 IDE
840: .  远程 HTTP 服务
841: .  远程 SSE 长连接 .  WebSocket 服务
842: ·  代理后的 claude.ai connector
843: .  当前进程内直接嵌入的 server
844: 很多项目会试图把这些都藏起来， 伪装成“统— client”； Claude Code 反而做得更诚实：它承认这些差异存在， 然后在统—入口里显式处理。
845: 7.3  connectToServer()   其实像一个连接工厂， 而不是一个普通connect 函数
846: 我觉得  connectToServer() 最厉害的地方， 不只是分 transport， 而是它把连接这件事拆成了—个完整生命周期：
847: .  构造 transport
848: ·  注入认证与 header ·  包装 timeout
849: .  建立  Client
850: ·  注册 request handler
851: ·  检查 capabilities / version / instructions ·  挂上 error / close handler
852: .  返回   connected / needs-auth / failed / disabled所以它输出的不是裸 SDK client， 而是：
853: Claude Code 自己语义下的  MCPServerConnection 。
854: 这—步非常关键， 因为只要这层抽象立住， 后面的上层代码就不必直接感知 SDK 的原始连接细节。
855: 7.4 认证设计说明作者知道“连接失败”里最大的一类其实是 auth
856: 这个文件里和认证有关的细节非常多：
857: .   McpAuth Error
858: MCP_AUTH_CACHE_TTL_MS .   isMcpAuthCached()
859: .   setMcpAuthCacheEntry()
860: .   handleRemoteAuth Failure()
861: .   createClaudeAi ProxyFetch()
862: .   checkAndRefreshOAuthTokenIfNeeded()
863: .   handleOAuth401Error()
864: 这背后的判断我很认同：
865: MCP 连接失败里最值得单独工程化处理的， 不是网络超时， 而是认证失效。
866: 作者做了几个非常产品化的处理：
867: 1. 401/needs-auth 不是简单失败， 而是独立状态
868: 2. needs-auth 会进入 15 分钟缓存， 避免反复探测
869: 3. 有 discovery 但没有 token 的 server 会被跳过， 避免空耗
870: 4. claude.ai proxy 的 bearer token 会在 401 后尝试刷新再重试—次
871: 5. 上层还能为 needs-auth server 生成  createMcpAuthTool(...)
872: 这说明 Claude Code 并不是把 auth 当“连接前置条件”， 而是把它当成 MCP 生命周期的—部分。
873: 7.5 它对连接稳定性的处理很成熟， 明显踩过真实坑
874: connectToServer() 后半段有很多很“脏”但很宝贵的逻辑：
875: .  连接超时保护·  stderr 捕获
876: ·  repeated terminal errors 计数
877: .   Maximum reconnection attempts 特判·  session expired 检测
878: ·  close 时清理 memo cache 和 fetch cache
879: 这类代码—眼就能看出不是“按文档写” 的， 而是被线上问题逼出来的。
880: 特别是这几个点很值得欣赏：
881: 1. SDK 的  onerror /  onclose 不完全可靠， 所以作者自己补了关闭和重连触发逻辑
882: 2. 远程 transport 连续错误达到阈值后会主动  closeTransportAnd RejectPending(...)
883: 3. session 过期通过 HTTP 404 + JSON-RPC   -32001 双信号识别
884: 4.  client.onclose 会主动清掉  connectToServer.cache 和  fetch*ForClient.cache
885: 这说明作者很清楚：
886: 在一个长生命周期Agent Runtime 里， MCP 最难的不是第一次连上， 而是掉线之后不挂死。
887: 7.6 它不是只连 server， 还把 MCP 能力转译成 Claude Code 自己的语言
888: 这—块我觉得是这个文件架构价值最高的地方之—。

894: Command
895: Resource
896: 这—步非常关键， 因为它说明 Claude Code 的宿主协议高于 MCP 原协议。
897: MCP 只是外部能力来源， 真正给模型消费的还是 Claude Code 自己的能力抽象。
898: 也就是说， Claude Code 并没有让 MCP 反过来定义自己的运行时；
899: 它做的是：
900: 把 MCP 吞进自己的运行时模型里。
901: 7.7  fetchToolsForClient()   特别能体现“协议映射层”这个角色
902: 这段代码不是简单把  tools/list 结果拿回来展⽰， 而是做了完整的能力翻译：

921: 7.8  getMcpToolsCommand sAnd Resources()   体现了真正的“总线装配”
922: 过程
923: 如果说  connectToServer() 是单连接工厂， 那么  getMcpToolsCommand sAnd Resources() 就是：

932: 这个设计非常适合Agent Runtime， 因为宿主可以逐步把可用工具开放出来， 而不用死等最慢的那个

957: 7.10 返回值处理这部分做得非常好， 明显不想让 MCP 把上下文炸掉

973: 这非常像—个成熟宿主在做的事：
974: 保护上下文窗口， 把外部返回值驯化成模型可承受的格式。
975: 7.11  callMCPToolWithUrl ElicitationRetry()   说明作者把 MCP 的交
976: 互式工具也接进来了
977: 很多人理解 MCP tool， 会把它想成同步 RPC。
978: 但这里专门有—层：
979: .   callMCPToolWithUrl ElicitationRetry(...)
980: 它处理的是 MCP 的  Url ElicitationRequired 错误， 也就是： tool 调用过程中要求用戶去完成一个 URL 交互。
981: 作者做的不是简单报错， 而是：
982: 1. 识别  -32042
983: 2. 解析 elicitation 列表
984: 3. 先跑 elicitation hooks
985: 4. 不行再走  handleElicitation(...) 或 REPL queue
986: 5. 完成后重试 tool call
987: 这件事很重要， 因为它说明 Claude Code 接入 MCP 时， 并没有假设外部工具都是“无用戶交互” 的。
988: 相反， 它接受了：
989: 某些外部能力本身就是半交互式协议。
990: 这又—次说明它的架构更像 runtime， 而不是调用器。
991: 7.12  callMCPTool()   是最后一道“协议脏活收口层”
992: 真正的原始调用在  callMCPTool() 里。
993: 它做的事情比你想象得多：
994: .  长时间工具调用进度日志·   自己再包—层 timeout
995: .  将 SDK progress 转成 Claude Code 的  mcp_progress .  处理  isError: true
996: ·   特判 401 -&gt;  McpAuth Error
997: ·  特判 session expired / connection closed -&gt; 清缓存并抛  McpSessionExpired Error .  成功后再走  processMCPResult(...)
998: 这—层非常像典型的 adapter gateway：
999: 它把 SDK 原始行为和 Claude Code 上层期望之间的缝隙都补上了。
1000: 所以如果让我—句话概括它， 我会说：
1001: callMCPTool()   负责把“不稳定的外部协议行为”翻译成“稳定的宿主错误语义与结果语义”。
1002: 7.13 这个模块最值得借鉴的地方
1003: 如果让我总结 src/services/mcp/client.ts 最值得学的地方， 我会给四个关键词：
1004: 1. 异构接入
1005: 2. 平台转译
1006: 3. 结果驯化
1007: 4. 连接韧性
1008: 异构接入， 是它承认 transport 和部署形态的复杂性。
1009: 平台转译， 是它坚持把外部能力映射成 Claude Code 自己的 Tool/Command/Resource。
1010: 结果驯化， 是它不让 MCP 原始结果直接冲进上下文。
1011: 连接韧性， 是它认真处理超时、掉线、401、session 失效和重连。
1012: 所以这文件真正厉害的地方， 不是“把 MCP 接进来了”， 而是：
1013: 它把 MCP 从一个外部协议， 接成了 Claude Code 自己的内生能力总线。
1014: 8. src/state/AppStateStore.ts： 运行时状态内核的总台账
1015: 前面几章我们已经分别看了：
1016: .  会话怎么跑

1018: .  子 agent 怎么调度
1019: 这时候自然会冒出—个问题：
1020: 这么多状态， 最后都放在哪里？
1021: Claude Code 的答案， 就落在 src/state/AppStateStore.ts 这—组文件上：
1022: .  src/state/AppStateStore.ts .  src/state/store.ts
1023: .  src/state/AppState.tsx
1024: .  src/state/onChangeAppState.ts .  src/state/selectors.ts

1026: 因为它做的事情不是写几个字段， 而是：
1027: 把 Claude Code 这台Agent Runtime 的“全部显性状态面”定义出来。
1028: 8.1 先说判断： 这不是普通 UI state， 而是整套运行时的共享控制面
1029: 很多项目里的  AppState 只是：

1036: ·  speculation / promptSuggestion 态·  tmux / browser / computer-use 态
1037: 这说明作者对AppState 的理解不是“前端页面状态”， 而是：
1038: 整个宿主运行时的共享状态总线。
1039: 也就是说， Claude Code 的 UI 只是这个状态的—种消费方；
1040: 真正被建模的是整套 runtime 本身。
1041: 8.2 AppState    的体量， 本身就是 Claude Code 架构复杂度的地图
1042: 如果你顺着 src/state/AppStateStore.ts 往下看， 会发现这个类型几乎就是 Claude Code 的模块目录展开图。
1043: 里面至少能看到这些大的状态簇：
1044: .  基础会话与显⽰：  verbose 、 statusLineText 、 expandedView .  模型与权限：  mainLoopModel 、 tool PermissionContext
1045: ·   远程与 bridge：  remoteSessionUrl 、 repl Bridge*
1046: .  任务系统：  tasks 、 foregroundedTask Id 、 viewingAgentTask Id
1047: .  MCP：  mcp.clients 、 mcp.tools 、 mcp.commands 、 mcp.resources
1048: .  插件：  plugins.enabled 、 plugins.errors 、 plugins.installationStatus ·   agent / team：  agentDefinitions 、 teamContext 、 agentNameRegistry
1049: .  通知与交互：  notifications 、 elicitation 、 inbox
1050: .  预测与建议：  promptSuggestion 、 speculation
1051: .  终端外设与工具态：  tungsten* 、 bagel* 、 computerUseMcpState
1052: 这非常值得注意， 因为它说明 Claude Code 的复杂度不是藏在各种 singleton 里， 而是：
1053: 尽量显式地暴露为统一状态面。
1054: 这种设计的好处是， 后面你分析系统时， 不用到处猜“状态藏哪了”， 直接看  AppState 就知道这系统到底在管理什么。
1055: 8.3 这个文件最重要的价值， 不是字段多， 而是它把状态边界一次性画清楚了
1056: 我觉得 src/state/AppStateStore.ts 最值得肯定的—点是：
1057: 作者愿意用一个很长的类型， 把系统边界公开写出来。
1058: 这比很多项目里“状态散落在 hook、context、模块变量、单例对象、React 本地 state”要健康得多。
1059: 因为—旦边界清楚， 后面很多事情都会变简单：
1060: 哪些状态可序列化
1061: .  哪些状态是进程内对象
1062: ·  哪些状态要跨 UI / runtime 共享·  哪些字段适合做 selector
1063: .  哪些更新应该触发副作用
1064: Claude Code 在这点上很像工程团队里经验比较足的—类写法：
1065: 宁可把状态总表写重一点， 也不把状态分散得找不到。
1066: 8.4 tasks  、 mcp  、 plugins   这些嵌套块， 说明它不是扁平 store，而是“领域分仓”
1067: 虽然  AppState 很大， 但它不是—股脑扁平铺开。
1068: 作者很明显在按领域分仓：
1069: .   tasks
1070: mcp
1071: .   plugins
1072: .   notifications .   elicitation
1073: .   workerSandboxPermissions .   promptSuggestion
1074: .   skillImprovement
1075: 这说明他不是没意识到复杂度， 而是在做—种很务实的控制：
1076: 在一个总 store 下， 按运行时子域分组。
1077: 这类结构比 Redux 风格的大量 reducer 切片更轻， 但又比“所有字段散着放”更可维护。
1078: 对—个 CLI + Ink + 多 agent + MCP 的混合系统来说， 我觉得这是—个合理折中。
1079: 8.5 tasks   被故意排除出  DeepImmutable ， 这说明作者对“状态纯度”和“工程现实”有取舍
1080: 这个细节很有意思。
1081: AppState 主体包了—层  DeepImmutable&lt;...&gt;， 但  tasks 被单独拿出来， 注释里明确说： .   TaskState contains function types
1082: 这其实暴露了—个很真实的工程取舍：
1083: 作者想让大部分状态都尽量不可变、可预测， 但承认任务对象里有些运行时句柄没法完全纯数据化。
1084: 这很像成熟工程而不是学院派工程。
1085: 真正复杂的运行时里， 总会有：
1086: ·   callback
1087: ·   abort controller ·  cleanup 函数      进程句柄
1088: 如果硬要把这些都纯数据化， 系统会变得很拧巴。
1089: Claude Code 在这里的做法是：
1090: 大面上保持不可变数据风格
1091: .  局部允许任务态保留运行时对象
1092: 这个平衡我觉得是理性的。
1093: 8.6  getDefaultAppState ()   很重要， 因为它不是默认 UI， 而是默认宿主
1094: 很多人看到  getDefaultAppState()， 会觉得这只是初始化。
1095: 但在 Claude Code 里， 这个函数的意义更大：
1096: 它定义的是“Claude Code 进程刚启动时， 整个 runtime 的零点状态”。
1097: 而且这份默认态不是随便填的。
1098: 它里面有不少有意思的系统级判断：
1099: ·  teammate 且  plan_mode_required 时， 初始 permission mode 设成  plan .   thinkingEnabled 走   shouldEnableThinkingByDefault()
1100: .   promptSuggestionEnabled 走   shouldEnablePromptSuggestion()
1101: .   tool PermissionContext 从  getEmptyTool PermissionContext() 起步 .   mcp 、 plugins 、 notifications 、 elicitation 全都有完整空态
1102: 这说明初始化不是“先给个空对象再说”， 而是：
1103: 把产品默认行为直接写进状态工厂。
1104: 这类默认态工厂非常关键， 因为它决定了系统在最复杂的 runtime 逻辑启动前， 先以什么姿态站稳。
1105: 8.7 真正的 store 原语其实非常小， 这反而是优点
1106: src/state/store.ts 很短， 核心只有：
1107: .   getState()
1108: .   setState(updater)
1109: .   subscribe(listener)
1110: createStore() 的实现也很干净：
1111: •   存  state
1112: .  存  listeners
1113: ·    setState 用函数式 updater
1114: .   Object.is(next, prev) 避免无效通知    .  可选  onChange({ newState, oldState })
1115: 这说明 Claude Code 的状态系统没有引入—个笨重状态框架， 而是自己保留了最小原语。
1116: 这背后的好处很明显：
1117: 1. React 外部也能用
1118: 2. 非 UI 逻辑也能安全持有  getState/setState
1119: 3. 调试时能很清楚知道状态更新机制到底是什么
1120: 这也是为什么它特别适合 Claude Code 这种“不是纯 React App”的系统。
1121: 因为这套运行时本质上有大量逻辑发生在 React 之外。
1122: 8.8 AppState .tsx   说明 React 在这里是消费者， 不是状态拥有者
1123: src/state/AppState.tsx 做的事情很清楚：
1124: .  用   createStore(...) 创建 store   用  AppStoreContext 提供出去
1125: .  用   useSyncExternalStore(...) 做选择性订阅
1126: .  暴露  useAppState() 、 useSetAppState() 、 useAppStateStore()这里最关键的设计取向是：
1127: 状态先存在， React 再去订阅它。
1128: 而不是：
1129: 状态存在于 React 组件树里， 其他地方再想办法取。
1130: 这对 Claude Code 这种系统太重要了。
1131: 因为它有很多更新来自：
1132: MCP 回调 .  任务系统 ·   bridge
1133: ·   server mode ·   tool runtime
1134: 这些地方很多都不是 React 组件。
1135: 所以把 store 放在 React 之下， 显然是不对的； Claude Code 的做法是把 React 放在 store 之上。
1136: 8.9  useAppState ( selector)    的写法很成熟， 明显在防大范围重渲染
1137: 这里作者没有写—个“拿整个 state”的粗暴 hook， 而是明确鼓励 selector 模式：
1138: .   useSyncExternalStore(store.subscribe, get, get)
1139: .  注释里提醒不要返回新对象
1140: ·  多字段就多次调用 hook  这说明作者意识到了—个现实：
1141: AppState 很大， 如果消费方式粗糙， 整个 Ink UI 会被状态更新拖垮。
1142: 所以他们通过 selector +  Object.is 做最小重渲染。
1143: 这不是特别花哨， 但非常有效， 也符合现在 React 官方比较推荐的 external store 用法。
1144: 8.10  onChangeAppState ()   其实是状态层与副作用层之间的桥
1145: 我很喜欢 src/state/onChangeAppState.ts 这个分层。
1146: 它的作用非常明确：
1147: 不是负责决定状态， 而是负责在状态变化后触发必要的外部同步。
1148: 里面已经能看到不少典型例子：
1149: ·   permission mode 变化 -&gt;  notifySessionMetadataChanged() /  notifyPermissionModeChanged() ·  mainLoopModel 变化 -&gt; 更新 settings 与 override
1150: ·  expandedView / verbose / tungstenPanelVisible -&gt; 持久化到 global config ·  settings 变化 -&gt; 清 auth cache、重置 env
1151: 这说明作者没有把副作用塞进每个  setState call site， 而是尽量把“状态变了之后要干什么”收进—个总diff 点。
1152: 这是非常成熟的设计。
1153: 因为—旦没有这个 choke point， 后面每个地方都可能：
1154: 改 state
1155: ·  顺手写 config       顺手发桥接事件
1156: 顺手清缓存
1157: 最后就很难追。
1158: 8.11 这张图能说明它为什么更像运行时状态总线， 而不是前端 store
1159: AppStateStore.ts
1160: 定义状态形状与默认态
1161: 提供初始结构
1162: store.ts  createStore
1163: 被 Provider 包装                                       状态变化触发
1164: AppState.tsx
1165: Provider + selector hooks
1166: 直接 getState / setState
1167: selector 订阅                                          同步外部系统
1168: Ink / React 组件                                                      工具运行时 / MCP / Agent /
1169: 这个图里最关键的—点是：
1170: React 只是右边一个消费方， 不是整个状态系统的中心。
1171: 这和很多纯前端应用完全不同。
1172: Claude Code 的 store 更像 runtime backbone。
1173: 8.12 这套状态层最值得欣赏的地方， 是“中心化定义， 去中心化消费”
1174: 如果让我总结这套状态层设计的优点， 我会用—句话概括：
1175: 中心化定义， 去中心化消费。
1176: 中心化定义体现在：
1177: ·   AppState —处定义系统状态面
1178: .   getDefaultAppState() —处定义默认宿主
1179: .   onChangeAppState() —处定义关键副作用桥去中心化消费体现在：
1180: ·  React 通过 selector 消费     非 React 代码直接拿 store
1181: ·  任务系统、MCP、bridge 都能经  setState 进入同—总线
1182: 这对 Claude Code 这种“宿主 + UI + 工具 + 多 agent + 远程桥接”混合系统来说， 我觉得是非常对路的。
1183: 8.13 这个模块最值得借鉴的地方
1184: 如果让我总结 src/state/AppStateStore.ts 这—组状态层设计， 最值得学的是三个关键词：
1185: 1. 显式
1186: 2. 轻量
1187: 3. 统—
1188: 显式， 是状态边界不藏。
1189: 轻量， 是底层 store 原语非常小。
1190: 统—， 是 UI、runtime、副作用都围绕同—份状态总线工作。
1191: 所以这组代码真正厉害的地方， 不是“ 字段很多”， 而是：
1192: 它把 Claude Code 的运行时复杂度收进了一个还能被人理解的状态骨架里。
1193: 9. src/bridge/bridgeMain.ts： 远端控制与桥接主循环
1194: 如果前面几个模块让我们看到的是 Claude Code 的本地 runtime，那么 src/bridge/bridgeMain.ts 看到的就是另—面：
1195: Claude Code 怎么把本地进程， 变成一个可被远端接入、可被远端恢复、可持续轮询工作的桥接宿主。
1196: 这个文件很重， 而且它的重不是“代码太长”， 而是职责密度非常高。
1197: 它至少同时负责：
1198: 1. 启动和注册 bridge environment
1199: 2. 轮询远端 work queue
1200: 3. 根据 work 孵化本地 session 子进程
1201: 4. 维持 heartbeat、token refresh、reconnect
1202: 5. 管理 worktree 与 session 生命周期
1203: 6. 处理 headless 模式与交互模式两套入口
1204: 所以我会把它定义为：
1205: Claude Code Remote Control 的主循环调度器。
1206: 9.1 先说定位： 它不是一层薄桥， 而是“远端控制 runtime”
1207: 很多系统里的 bridge 只是做两件事：
1208: .  收到请求
1209: 转发到本地
1210: 但 src/bridge/bridgeMain.ts 明显不是这种薄层。
1211: 它里面有自己的：
1212: .  参数解析 .  模式决策
1213: ·  environment 注册·   session spawn
1214: ·   poll/backoff/heartbeat ·   shutdown/cleanup
1215: ·   headless logger
1216: 这说明 bridge 在 Claude Code 里不是“补充功能”， 而是完整的运行时子系统。
1217: 换句话说， Remote Control 不是在 Claude Code 外面包—层壳，而是把 Claude Code 进程的—部分能力重新组织成—个：
1218: 可持续运行的远端会话代理。
1219: 9.2  bridgeMain ()   负责的是“把一堆配置与前置条件收敛成可运行桥”
1220: bridgeMain(args) 前半段其实很值得看。
1221: 它不是立刻去 poll， 而是先做了很多前置收敛：
1222: .   parseArgs(...)
1223: ·  multi-session gate 校验 .  trust 检查
1224: ·  auth 检查
1225: ·  baseUrl / sessionIngressUrl 决定 .  spawnMode 决定
1226: ·  resumeSessionId / continueSession 决定·  environment 注册
1227: 这说明作者没有把桥接理解成“只要token 对了就能开跑”， 而是明确认为：
1228: 桥接是一种受 workspace trust、auth、spawn mode、resume 语义共同约束的运行模式。
1229: 这点非常重要。
1230: 因为如果不先把这些条件收敛， 后面的 poll loop 再稳， 整体体验也会非常脆。
1231: 9.3  spawnMode   是这个文件里非常关键的产品抽象
1232: 这个文件反复出现  spawnMode， 而且不是摆设。
1233: 它至少涉及：
1234: .   single-session
1235: .   same-dir .   worktree
1236: 在桥接场景下， 这个抽象非常聪明。
1237: 因为远端控制不是纯“连不连得上” 的问题， 而是：
1238: 远端发起的新会话， 应该怎样落到本地工作区。
1239: 这里的三种模式其实对应三种产品哲学：
1240: 1.  single-session
1241: 只恢复—个会话， 生命周期强耦合， 偏传统 remote attach
1242: 2.  same-dir
1243: 多个会话共享当前目录， 追求轻量与即时性
1244: 3.  worktree
1245: 每个会话独立 git worktree， 追求并发安全
1246: 也就是说， 作者在 bridge 层讨论的已经不是传输协议， 而是：
1247: 远端协作时的工作隔离模型。
1248: 这比—般人理解的 bridge 要深很多。
1249: 9.4  runBridgeLoop()   才是真正的心脏
1250: 整个文件的核心毫无疑问是  runBridgeLoop(...) 。
1251: 如果让我只保留—个函数来代表这套桥接系统， 我会留它。
1252: 因为它把桥接系统最难的几个问题都放在—起解决了：
1253: ·  如何跟踪 active sessions .  如何轮询工作
1254: ·  如何在 at-capacity 时不忙等   ·  如何 heartbeat 现有 work item ·  如何更新 token
1255: ·  如何在 session done 时 stop work / archive / cleanup
1256: ·  如何在 shutdown 时优雅收尾这已经不是“轮询函数”， 而是：
1257: 桥接模式下的 session scheduler。
1258: 9.5 这套桥接循环不是简单 poll， 而是 “poll + heartbeat + backoff + wake” 的组合
1259: 我很喜欢  runBridgeLoop() 里对空闲和满载状态的处理。
1260: 它不是死循环  pollForWork()， 而是组合了几种节奏控制：
1261: .   pollForWork(...)
1262: .   heartbeatActiveWork Items()
1263: .   createCapacityWake(...)
1264: .   getPollIntervalConfig()
1265: .   connBackoff / general Backoff
1266: 这意味着作者已经意识到 bridge 场景下有几种完全不同的运行阶段：
1267: 1. 空闲无 work
1268: 2. 有 session 但未满载
1269: 3. 已满载， 需要 heartbeat 但不能继续接单
1270: 4. 网络抖动 / token 失效 / reconnect
1271: 如果只用—种固定轮询间隔， 这些阶段都会处理得很差。
1272: Claude Code 的做法明显更成熟：
1273: 让 poll、heartbeat、capacity wake 和 backoff 共同组成桥接循环。
1274: 这会让系统既不容易打爆服务端， 也不容易在 session 结束后反应迟钝。

1276: onSessionDone(...) 这段我很欣赏。
1277: 它不是简单记个日志， 而是在 session 结束时做—整套生命周期收口：
1278: .  从  activeSessions 、 sessionWork Ids 、 sessionIngressTokens 等 Map 删除·  取消 timeout timer
1279: ·  取消 token refresh
1280: .   capacityWake.wake()
1281: .  根据状态决定是否  stopWorkWith Retry(...) ·  清理 worktree
1282: ·   multi-session 下  archiveSession(...)
1283: ·   single-session 下  controller.abort()这说明作者很清楚：
1284: session 结束不是一个事件， 而是一组系统状态迁移。
1285: 这也是为什么我—直说 Claude Code 很像 runtime。
1286: 因为这种写法明显是把“会话” 当成受控生命周期对象， 而不是聊天窗口。
1287: 9.7 它对 session 恢复和 token 续租的处理很像生产系统， 而不是demo
1288: bridge 场景里最烦的—类问题， 往往不是第—次启动， 而是：
1289: ·  session 还活着， 但 token 过期了

1386: 10. src/server/createDirectConnectSession.ts： Direct Connect 会话握手入口
1387: 10.1 它不是“再写一个请求函数”， 而是在补齐 Server Mode 的第一步
1388: 如果只看 src/server/createDirectConnectSession.ts 这—个文件， 你会觉得它很薄：
1389: .  组—个  POST /sessions .  带上  cwd
1390: .  可选带  Authorization .  校验返回值
1391: ·  组—个内部 config 返回   但这正是它容易被低估的地方。
1392: 这个文件真正负责的， 不是“发请求”本身， 而是：
1393: 把一个外部 direct-connect server 的 HTTP 建连动作， 转成 Claude Code 内部可以继续托管的会话配置。
1394: 也就是说， 它是—个很薄的握手层， 不是—个完整 runtime。
1395: runtime 在别处； 但没有这—步， runtime 根本起不来。
1396: 10.2 为什么它重要
1397: Claude Code 到这里已经能看出两套非常不同的运行姿势：
1398: 1. 本地进程内直接跑会话
1399: 2. 通过 bridge / remote 方式托管远端工作
1400: 3. 通过 direct connect 连到—个 server 侧会话
1401: 前两种更像“宿主自己掌控全部生命周期”。
1402: 第三种则更像“宿主接入—个外部会话承载面 ”。
1403: 而 src/server/createDirectConnectSession.ts 正是第三种姿势成立的起点。它解决的问题是：
1404: 服务器怎么创建会话
1405: 当前客戶端工作目录怎样传过去   权限跳过标志怎样显式表达
1406: .  HTTP 返回怎样变成内部  DirectConnectConfig .  后续 WebSocket 连接该连哪—个  ws_url
1407: 所以它虽然小， 但位置非常关键。
1408: 它是 server mode 的入口握手面。
1409: 10.3 它的设计哲学非常“薄协议、厚下游”
1410: 这个文件最有意思的地方， 是它刻意不做太多事。
1411: 它没有：
1412: .  在这里维护长连接 .  在这里处理消息流
1413: .  在这里实现权限请求回调·  在这里做 session resume   在这里解析复杂控制协议
1414: 它只做三件核心动作：
1415: 1. 把输入压成 server 能理解的最小请求
1416: 2. 把响应校验成内部能信任的结构
1417: 3. 把错误包装成明确的  DirectConnectError
1418: 这是—种很成熟的边界切法：
1419: .  握手层只负责“建联成功”
1420: .  连接层负责“会话持续”
1421: ·  上层 runtime 再负责“消息编排与产品语义”
1422: 这比把所有 direct connect 逻辑塞进—个超级 manager 里更健康。
1423: 因为—旦以后 server API 变动， 你只需要先修握手面， 而不是把消息循环也—起搅乱。
1424: 10.4  cwd    与  dangerously_skip_permissions   暴露了它在传递“会话
1425: 初始化语义”
1426: 请求体非常短， 但很说明问题：
1427: .   cwd
1428: .  可选  dangerously_skip_permissions: true
1429: 这意味着 direct connect 建的不是—个抽象 socket， 而是—个：
1430: .  带工作目录 .  带权限模式
1431: .  准备运行 Claude 会话
1432: 的初始化请求。
1433: 这里很值得注意的—点是：
1434: dangerously_skip_permissions 没有被柔化成—个模糊配置名， 而是直接把危险性写进字段名里。
1435: 这和 Claude Code 前面权限系统的风格是—致的：
1436: .  危险能力不靠注释提醒
1437: .  危险能力直接进 API 命名
1438: 使用者必须显式承担语义成本
1439: 这种命名方式很“产品化”， 也很“ 安全工程化”。
1440: 10.5 它真正做的， 是把外部响应折叠成内部  DirectConnectConfig
1441: 看它的返回值就很清楚了：
1442: .   config.serverUrl
1443: .   config.sessionId .   config.wsUrl
1444: .   config.authToken .   workDir
1445: 这里最重要的不是字段本身， 而是—次 语义折叠：   server 返回的是—个建会话的 HTTP 响应
1446: .  Claude Code 内部真正需要的是—个能继续接管的连接配置也就是说， 外部协议世界里是：
1447: .   session_id .   ws_url
1448: .   work_dir
1449: 内部 runtime 世界里则是：
1450: .   DirectConnectConfig .  后续  WebSocket
1451: 会话消息回调   权限请求回调
1452: 这—步折叠做完之后， 上层代码就不必继续知道  /sessions 的 HTTP 细节了。从架构角度看， 这就是—个很标准的 anti-corruption layer。
1453: 调用方
1454: 传入 serverUrl / cwd / auth
1455: POST /sessions发送初始化请求
1456: connectResponseSchema
1457: 校验 session_id / ws_url / w
1458: DirectConnectSessionManag继续接管 WebSocket 会话
1459: 构造握手参数
1460: 折叠为内部结构
1461: 交给下游连接层
1462: 返回 JSON
1463: 10.6  connect ResponseSchema()   说明作者不相信“服务端一定返回对”
1464: src/server/types.ts 里这段 schema 很短：
1465: .   session_id: string
1466: .   ws_url: string
1467: .   work_dir?: string
1468: 但它的意义很大。
1469: 很多同类系统做到这—步时， 会直接：
1470: .   await resp.json()
1471: .  然后手写字段访问
1472: 失败就让异常自然冒泡
1473: Claude Code 没这么做， 而是坚持经过  connectResponseSchema().safeParse(...) 。
1474: 这说明作者对 direct connect 的定位很清楚：
1475: .  它不是“ 内部函数互调”
1476: ·  它是“跨进程 / 跨宿主 / 可能跨版本” 的协议边界
1477: 只要是协议边界， 就必须校验。
1478: 否则 server 版本稍微漂—点， 上层 runtime 就会带着半坏状态继续运行。
1479: 10.7  DirectConnect Error   说明这里在主动建构错误语义， 而不是放任底层异常泄漏
1480: 这个文件另—个我很喜欢的点， 是它专门定义了  DirectConnectError 。
1481: 这看起来只是—个薄包装， 但价值很实际：
1482: 1. 上层可以明确知道这类错误属于 direct connect 握手失败
1483: 2. 网络失败、HTTP 失败、响应解析失败都能被统—归类
1484: 3. UI / CLI / server mode 后续要做差异化提⽰时有了稳定类型
1485: 它没有把：
1486: .   fetch 错误    .   resp.ok 错误
1487: ·  schema parse 错误
1488: 原样甩给上游， 而是统—收束成—个产品语义错误。
1489: 这和很多“工程上能跑就行 ”的实现差别很大。
1490: Claude Code 明显更在意： 上层最终拿到的到底是不是一个可叙述、可处理、可呈现的错误。
1491: 10.8 跟 src/server/directConnectManager.ts   连起来看， 层次就完
1492: 整了
1493: 单看 src/server/createDirectConnectSession.ts 会觉得它很薄；
1494: 但和 src/server/directConnectManager.ts —拼， 层次就很清楚：
1495: ·    createDirectConnectSession.ts 负责建 session
1496: ·    directConnectManager.ts 负责维持 session后者真正处理的是：
1497: .  建 WebSocket .  收  SDKMessage
1498: .  过滤  keep_alive
1499: .  识别  control_request
1500: .  处理  can_use_tool 权限请求 .  回发  control_response
1501: .  支持  interrupt
1502: .  管理连接状态与断开
1503: 所以 direct connect 不是—个文件， 而是—个分层模型：
1504: 1. HTTP 握手层
1505: 2. WebSocket 会话层
1506: 3. 上层 runtime / REPL / headless runner 集成层
1507: 这才是这组模块真正值得学的地方。
1508: 不是“代码多高级”， 而是它把—个跨进程会话问题拆成了正确的三个边界。
1509: 10.9  directConnectManager .ts   暴露了 Claude Code 对“远端会话”采用的是流式控制协议， 而不是 REST 轮询
1510: src/server/directConnectManager.ts 里， 消息接入是 WebSocket， 且是逐行 JSON 解析：
1511: .   message 事件
1512: .   data.split('\\n')
1513: .   jsonParse(line)
1514: .  识别  StdoutMessage然后再把不同类型分流：
1515: .   control_request
1516: .   control_response .   keep_alive
1517: .   streamlined_text
1518: .   streamlined_tool_use_summary   system.post_turn_summary
1519: 其他真正需要上送给宿主的  SDKMessage
1520: 这说明 direct connect 的本质不是“远端 HTTP API”， 而是：
1521: 服务端托管 Claude 会话， 客户端通过结构化流协议接管交互。
1522: 也就是说，  createDirectConnectSession.ts 只是拿到这条流的入场券。
1523: 10.10 这套设计的优点与代价
1524: 优点很明显：
1525: 1. 握手层足够薄， 便于维护
1526: 2. 错误语义清楚， 便于产品层提⽰
1527: 3. schema 校验严谨， 适合协议边界
1528: 4. 与  directConnectManager.ts 的职责分层很干净
1529: 5. 给 REPL / headless runner 提供了统—的 direct connect 入口
1530: 代价也有：
1531: 1. 逻辑分散在多个文件里， 第—次读不容易—眼看全
1532: 2.  createDirectConnectSession.ts 太薄， 单文件可见价值容易被低估
1533: 3. direct connect 协议的真实复杂度被“藏”到了 manager 和上层 runtime 中但总体上， 我会认为这不是缺点， 而是成熟架构常见的观感：
1534: 真正重要的边界， 往往长得都不显眼。
1535: 10.11 这个模块最值得借鉴的地方
1536: 如果让我总结 src/server/createDirectConnectSession.ts 最值得学的点， 我会给四个关键词：
1537: 1. 握手边界
1538: 2. 协议折叠
1539: 3. schema 校验
1540: 4. 错误语义
1541: 它的价值不在“逻辑多”， 而在“位置准”。
1542: 它非常准确地站在 server API 和本地 runtime 之间， 把：
1543: .  外部响应
1544: .  内部配置 .  失败语义
1545: 收成—个干净的入口。
1546: 这就是为什么我会说， 这文件虽然薄， 但它不是边角料。
1547: 它是 Claude Code 在  server / direct connect 这条支线上的 会话握手层。
1548: 11. src/utils/plugins/loadPluginCommands.ts： 插件内容接入宿主命令协议的总适配层
1549: 11.1 先说判断： 它不是“扫插件目录”， 而是在做插件内容协议转换
1550: 如果你把 src/utils/plugins/loadPluginCommands.ts 当成—个普通 loader， 就会低估它。
1551: 它表面上在做这些事：
1552: .  读取插件目录 .  找  .md
1553: ·   读 frontmatter
1554: ·  生成 slash command
1555: 但真正发生的事情是：
1556: 它把插件作者写的 Markdown 内容， 转换成 Claude Code 宿主内部统一可执行的  Command    协议对象。
1557: 这意味着它不是文件系统工具， 而是—个协议适配层。
1558: 插件世界里的材料很多：
1559: .   commands/ 目录 .   skills/ 目录
1560: .   plugin.json 里的  commands
1561: ·  manifest 里的 metadata override   内联  content
1562: .  用戶配置项
1563: .   ${CLAUDE_PLUGIN_ROOT} 、 ${CLAUDE_SKILL_DIR} 之类变量·  prompt 里的 shell 执行
1564: 而这个文件做的， 就是把这些异构输入压成 Claude Code 自己那套统—命令模型。
1565: 11.2 为什么它重要
1566: 插件体系真正要回答的问题不是“能不能装插件”， 而是：
1567: 插件写出来的东西， 最后怎样以宿主能理解、能授权、能展⽰、 能执行的方式挂进去。 src/utils/plugins/loadPluginCommands.ts 就是这个答案。
1568: 如果没有这层， 插件命令会很快退化成：
1569: .  —堆特殊格式
1570: —堆分支加载器
1571: .  —堆插件专属执行逻辑
1572: 最后宿主里的 slash command 体系会被插件体系撕裂。
1573: 而 Claude Code 没走这条路， 它坚持把插件命令折叠回统—  Command 。
1574: 11.3 这文件最厉害的地方， 是命令与技能在这里被部分统一了
1575: 虽然文件名叫  load PluginCommands.ts， 但它其实同时负责两件事：
1576: .   getPluginCommands()
1577: .   getPluginSkills()

2689: 27.2 这个文件最成熟的点， 是它不把所有失败都当成同一种失败
2690: 这里有几段判断特别能说明问题。
2691: 第—，  FOREGROUND_529_RETRY_SOURCES 明确区分了：
2692: 用戶正在等结果的前台请求
2693: 用戶根本感知不到的后台请求
2694: 只有前者才值得在容量雪崩时继续重试。
2695: 后者要尽快失败， 避免放大网关压力。
2696: 第二，  isPersistentRetryEnabled() 又引入了“无人值守会话” 的第三种世界：

2701: .  人在等， 就可以多扛—下
2702: 人看不见， 就尽量别放大故障
2703: 人不在， 但任务必须跑完， 就进入持久重试
2704: 这是很强的系统设计意识。
2705: 27.3 fast mode、fallback、认证恢复被收进同一条故障链， 非常像线上系统
2706: 这个文件最“线上” 的地方， 是它没有把错误处理拆成很多互相不知道彼此存在的小 util， 而是把真实故障链条收在了—起。
2707: 比如：
2708: ·  fast mode 遇到短  retry-after， 直接短等后保留 cache 继续
2709: ·  fast mode 遇到长等待， 进入 cooldown， 切回标准速度， 避免 cache thrashing .  连续  529 达阈值时， 可能触发  fallbackModel
2710: ·  遇到  ECONNRESET /  EPIPE 这种 stale connection， 会禁用  keep-alive
2711: ·  Bedrock / Vertex 的认证错误， 会清掉各自云凭证缓存·   401 / OAuth revoked 会强制刷新令牌
2712: 这意味着 src/services/api/withRetry.ts 处理的其实不是“重试次数”， 而是：
2713: 一次模型调用在复杂线上环境里可能经历的故障路径图。
2714: 所以它会显得很重， 但这正是因为它吸收了真实世界的复杂度。
2715: 27.4 它用  AsyncGenerator   往外吐系统消息， 这一点非常漂亮
2716: with Retry() 最值得夸的设计之—， 是它不是简单返回—个  Promise&lt;T&gt;， 而是：

2720: ·  keep-alive 风格的 retry 提⽰
2721: 于是上层 runtime 不会只知道“还没返回”， 而是能把这段等待重新编进 Claude Code 的消息流。
2722: 这件事非常关键， 因为 Claude Code 是产品， 不是库。
2723: 当—次请求卡在重试期时， 宿主需要的是：

2897: 29. 模块级评价
2898: src/main.tsx
2899: 评价： 系统总装层， 工程能力强， 复杂度也最重。优点是启动、模式、入口 、初始化全都统—。

2901: src/Tool.ts
2902: 评价： 平台契约层， 非常成熟。
2903: 它把 Tool 做成了完整运行时组件， 而不只是函数。
2904: src/QueryEngine.ts
2905: 评价： 会话控制器， 方向完全正确。
2906: 它证明作者理解 Agent 的本质是 session runtime。
2907: 问题主要是体量大， 不是抽象错。
2908: src/tasks/LocalAgentTask/LocalAgentTask.tsx
2909: 评价： 多 agent 产品化能力的核心证据。
2910: 它说明 Claude Code 做的是任务调度式多 agent， 而不是递归式多 agent。
2911: src/tools/AgentTool/AgentTool.tsx
2912: 评价： 多 Agent 路由与调度层， 非常关键。
2913: 它把“生成子 agent”从—个普通工具动作提升成了运行时分流决策。
2914: 如果没有这—层，  LocalAgentTask 再强， 也只是任务容器， 而不是完整的多 Agent 入口。
2915: src/hooks/useCanUseTool.tsx
2916: 评价： 权限编排层， 产品味非常浓。
2917: 它最厉害的地方不是安全规则本身， 而是把自动检查、人工审批、远端审批、swarm 授权统—进—套可竞争的决策流程。
2918: 这说明 Claude Code 的权限系统不是附属功能， 而是运行时的—部分。
2919: src/services/mcp/client.ts
2920: 评价： 外部能力总线适配层， 工程成熟度很高。
2921: 它把连接、认证、转译、容错、结果压平全都收在—起， 体量很重， 但方向是对的。
2922: 如果没有这—层， Claude Code 的 MCP 只能算“外挂能力 ”； 有了这—层， 它才真正变成宿主的—部分。
2923: src/state/AppStateStore.ts
2924: 评价： 运行时状态骨架， 重要性被低估。
2925: 它不是最耀眼的模块， 但它决定了前面那些复杂能力最后是否能收敛到—个统—控制面里。
2926: 如果没有这—层， Claude Code 会很快退化成—堆局部状态和隐式耦合。
2927: src/bridge/bridgeMain.ts
2928: 评价： 远端控制主循环， 工程味非常重。
2929: 它把 Remote Control 做成了真正可持续运行的 session 托管层， 而不是“把本地界面投到远端”。这也是 Claude Code 能从本地工具走向跨设备连续体验的关键模块。
2930: src/server/createDirectConnectSession.ts
2931: 评价： 服务端会话握手层， 文件很薄， 但边界切得很好。

3002: 如果让我用—句话总结这篇模块级拆解， 我会说：
3003: Claude Code 这套系统最厉害的地方， 是它把“模型能力”放进了宿主、会话、状态、协议、权限、接入、插件折叠、技能装配、调度、任务、桥接、握手、流控、装载治理、命令编排、远端托管、 内核状态、模型请求、SDK 数据骨架、控制协议、Query 配置快照、停点编排、沙箱边界、provider 适配、重试与退避策略、remote transport、token 预算二十七层结构里。
